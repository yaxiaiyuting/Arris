## 一、症状（你给的探针数据，先原样记下）

| 现象 | 数据 |
|---|---|
| 相位每 5 帧走 `0.206 × 5`，第 6 帧被覆盖回 0 | `sinceBarMs` 只在 `{0.00, 41.18}` 两个值之间跳 |
| 逐帧位移不匀 | 每帧 `0.206` 格，第 6 帧一次 `1.176` 格 |
| 每次归零都让画面向右回退 | `0.824 → 0.000` |

你在上一轮已经把根因收窄到一句话：
**锚点式子 `frameClockMs − clockOffsetMs − pendingArrivalMs` 拿两个时钟相减。**

这句话是对的，而且本轮把它量全了。

## 二、根因：那个「帧时钟」根本不是时钟

`frameClockMs` 是 `WaveformRing` **自己按 `dt` 累加**出来的：

```kotlin
frameClockMs += dtForPhase.toLong()   // ← 每帧截断一次
```

而 `pendingArrivalMs` 是音频线程用 `SystemClock.uptimeMillis()` 打的。两个量相减，
差值里就带着累加时钟的**系统性偏慢**：

| 面板 | 每帧 `dt` | `.toLong()` 丢掉 | 每秒 |
|---|---|---|---|
| 60Hz | 16.667ms | 0.667ms | **4.0%** |
| 120Hz | 8.333ms | 0.333ms | **4.0%** |
| 146.2Hz | 6.840ms | 0.840ms | **12.3%** |

差值单调跑负 ⇒ 相位被钉在 0 或顶棚上跳，**每一格都丢掉一帧的位移**，
下一格再补回来 —— 这正是你量到的 `{0.00, 41.18}` 与 `0.824 → 0.000`。

### 为什么上一版会把它当成「有意的补偿」

v3.4.4 留下的那条注释写着：把 `.toLong()` 改成四舍五入后，项目自己的两条判据**同时变红**
（最大步 5.88 倍名义、相位停顶棚 478/1080 帧），于是向下取整被当成「在替某处偏差打掩护」，
并写明「在这个偏差被量出来之前不要动这一行」。

现在真相是：**那个偏差就是它自己**。分母（柱间隔）曾在 UI 消费处被 vsync 量化成
100/116.7/133.3ms（v3.3.2 已修），而帧时钟又在被截断 —— 两处偏差在互相抵消一部分，
**谁单独改都会让另一处露出来**。所以「删掉锚点」和「只改取整」都被同一批判据否掉，
不是判据太严，是模型里同时存在两个错。

## 三、修法：相位只由两个**真实**时间戳相减得到

1. **环不再攒任何时钟**。`frameClockMs` / `clockOffsetMs` / `pendingArrivalMs` 三个字段整个删掉。
2. `pump` 多收一个 `nowMs` —— 帧循环把**它自己那一帧的时间戳**原样传下去
   （`withFrameNanos` 的 `frameTimeNanos / 1e6`）。它与音频线程的 `SystemClock.uptimeMillis()`
   **是同一个单调时钟基准**，本轮探针在真机口径上实测差值 ≤ 1ms（就是回调延迟）。
3. 相位 = `nowMs − 最后一根被消费的柱的到达时刻`，**不折回、不清零**。

第 3 条是你点出来的关键约束，也是本次唯一一处**判据口径**的修订：

> 到达帧上相位 =（这一帧比那根柱晚了多少）÷ 柱间隔，本来就该是个小正数。
> 要求它严格为 0 会把这一帧的位移丢掉 —— 少一截、下一帧再补回来。

所以新判据不是「相位不许超过 1」，而是**到达帧的位移必须 ≈ 名义步长**。

`foldScrollPhase` 与它的单测**保留**：调用方不给帧时钟时（老调用点 / 单测）仍走那条累加路径。

## 五、未验证项（如实）

1. **没有真机。** 本轮开工时原设备已从 `adb devices` 消失（你已告知真机不可用），
   探针数据全部来自 **API 33 模拟器**。模拟器的 vsync 是合成的、`dt` 实测 sd = 0.000ms ⇒
   「帧时间抖动下相位是否仍然匀速」只有 JVM 仿真的支持，**没有真机证据**。
2. **没有肉眼观感验证。** 本环境无法渲染这条波形（它只在横屏大屏 / 平板宽屏挂载）。
   「抽搐是否消失、顺不顺」最终要靠你看。
3. **release 包没有做帧时间测量**（铁律 16）。本版是纯逻辑改动（删状态、改一次减法），
   没有新增逐帧分配、没有新增绘制，但**不声称**任何 release 包帧时间结论。
4. **相位在「柱子迟到」时仍会短暂停在 1.0 顶棚**（等到下一根柱到达）。
   这是诚实的「等待」而不是缺陷：分母是到达处实测的间隔，柱子比估计的迟多少就等多久。
   JVM 仿真的理想时间线上它出现 0~2% 的帧；旧模型是 0（因为它把相位清零、代价是丢位移）。
   真机上这个比例取决于音频回调的抖动，**未测**。
5. **只有三泳道这一条渲染路径是改到的**。单条曲线降级路径不读相位（它走屏幕坐标系的平滑），
   行为未变、也未复测。

## 六、与上一轮「不发新包」决定的关系

上一轮你把波形回退到 v3.4.6、不发新包，理由是「剩下预算不足以把第四个模型做完并用探针验证」——
这个判断在当时是对的：**前三个模型确实都不成立**，而不是实现没调好。

本版把第四个模型做完了，并且补上了两样上一轮缺的东西：
**一个能判定「这一帧位移有没有被丢掉」的判据**，以及**同一把尺子下的改前基线**。
这两样才是让这次改动可验证的东西，模型本身只有三行。
