## 一句话

**三个「静默丢数据 / 静默不下发 / 静默不响应」的系统性缺陷被修掉，托盘补上缺失的上一首按钮并改成三层布局，聚合搜索不再把「还没回来」显示成「0 首」。**

## 1. R8 把持久化字段名混淆成单字母 —— **三个**落点，其中两个此前从未被发现

前几版已经修过四次（本地歌单 / 歌单缓存 / 匹配缓存 / 搜索历史）。本版做了一次**全仓扫描**，
对照 55 万行的 `mapping.txt` 与 APK 的 dex 反汇编，**又找到三个**：

| 落点 | R8 实际映射 | 你原本会遇到什么 |
|---|---|---|
| 离线曲目索引（`ncrust_offline/tracks`） | `songId→a` … `completedAt→i` | **离线曲目清单静默消失**（缓存字节还在，列表空了） |
| 每首歌的续播进度（`ncrust_playback_state/song_positions`） | `posMs→a, savedAtMs→b` | **续播位置与时间戳对调**，或「这应用不记住我听到哪」 |
| 收藏的专辑（`ncrust_library/saved_albums`） | `albumId→a` … `songCount→e` | `albumId` 读成 0 ⇒ **收藏页直接打不开**（列表 key 重复） |

它们共同的特征是**不崩**：同一个 APK 内读写自洽，只在下一次构建的混淆映射变化时静默丢数据。
所以「靠 code review 发现」是无效的 —— 上面第二个、第三个就藏在最显眼的地方。

**修法**：写路径只经 DTO、每个字段显式 `@SerializedName("<稳定名字>")`；
读路径同时认三种形状（稳定名字 → 已知旧单字母 → 未知时按声明顺序兜底）；
坏数据**逐条**丢弃而不是整段丢光。

**老数据不会丢 —— 这条在真机上端到端验证过**：
从一台还留着上一版数据的设备里取出一条**真实的旧形状**记录
（`{"a":503616,"b":"EM10_C_Long_Premix#070705",…}`），原样注入到另一台装了新版、
有 47 条记录的设备上，冷启播一首歌触发一次整表重写，再回读：

- 条数 **47 → 48**（一条没丢）；
- 字段名全部变成稳定名；
- 注入的那条**每个字段都正确**（歌名 / 艺人 / 档位 `jymaster` / 完成时间都对）。

**没有用「加一条 keep 规则」当手段**：加 keep 只影响将来写出来的形状，对已经落盘的
`a`~`i` 一点用都没有，还会改掉全局混淆映射、把静默丢失换到别的类上。

**防复发**：新增 `PersistenceFieldNameContractTest`，四件套 ——
DTO 注册表逐个反射断言「每个字段都有 `@SerializedName` 且不是单字母」、
keep 白名单断言（走 keep 路线的五个包规则还在；`cache.**` 则**不许**有）、
扫遍全部源码的 `@SerializedName` 检查，以及一条**反证用例**确保扫描器真的在扫。

## 2. QQ 的 id 被上报给了 ncm —— 真机上复现过的跨源数据泄露

`PlayReporter`（ncm 的播放上报）原来的卫语句里有一条 `songId > 0`。
而 qm 的数字 id 是用 `1L shl 62` 合成的（为了和 ncm 的 id 空间结构性隔离），
**它是正数** —— 所以那条卫语句在数学上不可能拦住它。

真机上复现到的样子（Android 16 的设备，上一版）：

```
NcrustTrack: restore -> track=qqmusic:4611686018784987997 …
PlaybackService: onStartCommand action=next
D/PlayReporter: weblog resp: 200 duration=0/0     ← 一个 QQ 合成 id 被 POST 给了ncm
```

**修法**：唯一判据是 bit62（`SourceIds.isQqId`）—— 不用 id 区间启发式（QQ 裸 songid 与
ncm id 同样是 9~10 位十进制，区间完全重叠），也不用散列反推（不可逆）。
闸门挂在**唯一的网络出口**上，而不是在各个调用点各判一次。
反方向（非 QQ id 上报给 QQ）也一并定义 —— 一条只写在文档里的规则拦不住下一个加 QQ 上报的人。

被拦下的次数只落**本地私有目录**（`ncrust_report_gate`，无网络出口），
埋点点位只做一次原子自增，落盘只在退出应用与 debug 诊断入口两处。

## 3. 竖屏托盘：补上从来没有过的「上一首」，并改成三层布局

任务书假定上一版把托盘的上一首按钮「删了或挤没了」。**探针推翻了这个前提**：
`git log -S "SkipPrevious" -- PlayerCard.kt` **零命中** —— 它从来没有存在过。
所以这不是回归修复，是补一个核心功能。

**三层布局**（你的要求）：

```
实时歌词                    ← 第一行，主题色
歌名                        ← 第二行，独占一行、主视觉
作者                  音源  ← 第三行，左对齐 + 右对齐
```

托盘高度 **56dp → 80dp**。这个数字是实测定的：三行文本的排版盒合计正好 56dp，
而 56dp 的托盘上下各只剩 0dp 留白（用真机截图做逐行像素剖面量出来的）。
封面保持 56dp 不跟着涨 —— 否则窄屏的文本列会从 136dp 掉到 112dp，而封面并不需要那 24dp。

**一个高度，四个消费者，本版把它们收进唯一落点（`TrayLayout`）**：
托盘本体、卡片收起时的落点计算、列表底部预留、封面落点中心。
旧写法是四处各写一份 `56.dp` —— 只改一处会得到「卡片与托盘之间露出一条空白带」
或「列表最后一项被托盘盖住」，两个症状都与「托盘高度」在代码上看不出关联。

**播放控制区**：上一首 / 播放暂停 / 下一首（48dp 触摸区，都补了无障碍标签）。
有意**不加**第四个按钮：三个已经占 144dp，窄屏文本列只剩 136dp，再加一个就会让三层塌成两行。
有意**不做**跑马灯：托盘在播放全程常驻，跑马灯会持续排帧，与「UI 动效不得影响播放性能」直接冲突。

**点击区域**：点歌词 = 展开播放器并直接看歌词；点作者 = 进艺人页；点歌名 = 展开播放器
（与整条托盘同一条命中路径）；点音源**不做**独立动作（三个候选动作都否决了，理由见报告）。

### 附带修掉一个真机测出来的缺陷：乱序模式下的「上一首」在轮首完全没反应

第一次受控复测（5 次）只有 **1/5** 成功，而非乱序下每次都成功。查落盘状态发现当时是
**乱序模式**，而乱序分支的代码是 `if (shuffledPosition > 0) { … }` —— **没有 else**：
游标在轮首时整个分支什么都不做，点了没有任何反馈、没有提示、没有日志。

改成**轮首回绕到轮末**（与「下一首」的队尾回绕、与顺序/列表模式的上一首同一条约定），
判定抽成纯函数 + 7 条单测。修复后同一脚本复测：**5/5 成功，每次 1 秒内响应**。

## 4. 搜索「晴天」先显示「qm 0 首」，5 秒后才变对

这是追加任务里的那条。探针把归因做实了：

- **不是** token 初始化（搜索路径零 token、零签名）；
- **不是** 结果映射慢（纯 JSON 遍历，上界 ≤0.3s）；
- **不是** 循环重试（只有一条一次性兜底通道，本轮 45 次全未触发）；
- **是**两件事叠在一起：① 两个音源是**串行**请求的（整体耗时是**和**而不是**最大值**）；
  ② QQ 的搜索接口本身慢（TTFB **P50 1722ms / P95 2989ms**，同网段直连实测）。

**「0 首」那句假话是类型问题**：统计量只有「两个整数」这一种表示，
于是「QQ 还没回来」被迫写成 0。逐帧量过：那句假话在屏幕上挂了 **2.2~2.7 秒**。

**本版做了三件事**：

1. **未返回时显示「搜索中…」，不显示 0**。真的 0 首（已返回且为空）照常显示 0 ——
   两者在类型上现在是可区分的事。
2. **两个源改为并发发起**。发布顺序一个字没改（仍然是 ncm 一到就上屏、QQ 到手再补），
   只是不再让 QQ 白等 ncm 那一段。
3. **超时与失败各说各的话，并给一条可点的手动重试**。
   不做自动重试 —— 那会在你已经往下翻的时候突然往列表里插结果。

顺带修了一个既有缺陷：外层 `catch` 把 `CancellationException` 当成普通异常，
于是**每敲一个字都会触发一次「取消 → 写错误 → 清空结果」**。现在取消原样抛出。

> **本版没做但已量化**：QQ 的兜底通道 `musicu` 实测 P50 只有 **376ms**，比现用的
> legacy 通道快约 **5 倍**。换主通道会改掉结果形状、回归面无法在本版验证完，
> 所以留到 v2.5.6，数字先记在这里。

## 5. 另外三件小的

- **搜索历史显示音源角标**。同名历史（同一关键词下两源会返回逐字同名的条目）
  现在右侧带 `qm` / `ncm` 角标，且角标贴右、不会被省略号吃掉。
- **平板补上「大屏幕模式」入口（⤢）**。此前在平板上**结构性不可达**（那个按钮只存在于
  竖屏控制条变体里，而平板恒走宽屏布局）。判据是「平板 且 不在大屏」，
  手机横屏一格都没变（六格 A/B 矩阵 + 5 条单测）。
- **macrobenchmark 的测量工具修好了**：迭代数与编译模式改成运行时可传
  （`-e ncrust.bench.iterations 3 -e ncrust.bench.compilation ignore`，不传参数时与原行为逐字节相同），
  修了一个**会把设备动画永久关掉**的脚本 bug（原值本来就是 `null` 时还原被短路），
  并把「必须用 release 包测量」从一句警告改成硬断言。

## 真机验证

| 设备 | 系统 | 内容 |
|---|---|---|
| PLC110 | Android 16 | 托盘三层 + 上一首 5/5 + 点作者 / 点歌词 + 搜索加载态逐帧 + R8 迁移闭环 |
| WGR-W09（华为平板） | Android 12 | 平板托盘 + macrobenchmark |
| SM-G9209 | **Android 7.0（API 24）** | release 包冷启不崩 + 老数据形状取证 |
| API 34 平板 AVD（强制竖屏） | Android 14 | 平板竖屏托盘 |

**macrobenchmark（release 包，`CompilationMode.Ignore` × 3 迭代，WGR-W09）**：

| 基准 | 指标 |
|---|---|
| 播放器展开 / 收起（帧 CPU 时间） | **P50 4.73ms / P90 8.71ms / P95 9.92ms / P99 12.30ms** |

**结论**：P99 = 12.30ms **低于 16.67ms 的一帧预算** —— 这条「文案转发属性最密集 +
每帧读动画值」的路径在这台设备上**没有超预算帧**。转发属性在动画路径上的开销**不显著**。
（这是本版建立的口径；上一版没有可比的 release 基线，所以不做版本间对比。）

**单测 / 静态**：1316 个 JVM 用例全绿（95 个测试类）；lint **0 Error / 0 Fatal**。

## 未验证 / 已知缺口（**如实列出，不当成已解决**）

1. **Android 7.0 真机的界面层验证没做成** —— 那台设备是 PIN 锁屏，Android 7 上
   `locksettings` 二进制不存在、`settings put secure lockscreen.disabled` 与
   `wm dismiss-keyguard` 都无效。**没有**用 root 去删它的锁屏口令文件
   （那会破坏你设备的锁屏）。API 24 上验证了「冷启不崩」与「老数据迁移」，
   但界面触摸用的是 Android 16 真机与 Android 14 平板模拟器。
2. **音源闸门没有 v2.5.5 的真机日志闭环**：需要构造一首可播放的 QQ 曲目并把进度推到 80%。
   行为由 16 条单测覆盖（含 bit62 边界与双向对称），但**没有真机日志**。
3. **三条 macrobenchmark 基准跑不了，根因已定位**：这个仓库根本没有依赖
   `androidx.profileinstaller` 库（release 与 debug 的清单里都没有它），
   只有 AGP 打进 APK 的 `baseline.prof` 资产。后果有两条 ——
   ① 需要丢 shader cache 的三条基准结构上跑不了；
   ② **API 24~30 的设备永远不会安装这份 baseline profile**（那个库才是安装器），
   冷启动会比应有的慢。这是**既有**问题，修它要加依赖并重新构建 ⇒ v2.5.6 候选。
4. **PLC110 上跑不了 macrobenchmark**：设备侧报 `UiAutomationService already registered`
   （该机启用了两个第三方无障碍服务，且无残留 instrumentation 进程）。
   没有为了跑基准而重启你的手机 —— 改用华为平板（同为 release 包）。
5. **平板 ⤢ 入口只有纯逻辑单测，没有真机点击证据**：华为平板的 `wm` 尺寸/旋转 override
   未被 EMUI 采纳（实窗仍是横屏），模拟器上时间不够。
6. **华为/荣耀控制中心卡片：一个字节未动**（不在范围内）。

## 升级提示

- 覆盖安装即可，**登录态与离线缓存都会保留**。
- 本版第一次运行时会把你已有的离线曲目索引、续播进度、收藏专辑**从旧的混淆字段名
  原地迁移到稳定字段名**（一次写入，之后不再变）。迁移不会丢数据（见上文真机闭环）。
- 托盘变高（56 → 80dp），列表底部预留同步加大；这是为了让「歌词 / 歌名 / 作者·音源」
  三行不再挤在一起。
- 如果你在用**乱序播放**，上一首按钮现在在轮首也会响应了（此前是静默无反应）。
