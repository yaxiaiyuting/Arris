# 探针 3.4 · 性能预算（v3.0.0）

> **性质**：只读探针 + 已落地实现的代价清单。
> **证据分级**：**【实测】**= 真机 / 仪器探针跑出来的数字（附产出文件）；**【事实】**= 源码；
> **【估算】**= 代码算式；**【未验证】**= 明确没确认。

## 1. v2.9.0 基线（**原文照抄，不重新推导**）

| 轮次 | 设备 / 形态 / 档位 / 界面动效 | Total / 30s | Janky | P50 | P90 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| `s6-portrait-t1-ui` | S6 竖屏展开 · 精致 · 开 | 1129 | 860 (76.17%) | **21ms** | 30ms | 34ms | **150ms** |
| v2.6.2 真基线（同设备同方法） | S6 · 旧波形 | 944 | 366 (38.77%) | 15ms | 25ms | 27ms | 31ms |
| v2.8.0 · T0 | S6 · 简洁 | 963 | 884 (91.80%) | 20ms | 27ms | 31ms | 46ms |
| v2.8.0 · T1 | PCL110 · 精致 | 1821 | 5 (0.27%) | 7ms | 9ms | 11ms | 14ms |

来源：`docs/verification/v2.9.0/EVIDENCE.md` §3.1 与 §1；
**验收口径因此是「S6 稳态 P99 不劣于 v2.9.0」**，不是「回到 P50 15」（那要回退波形实现）。

所以 **P50/P90 比 P99 更能说明问题**。

## 2. v3.0.0 新增的代价（逐项，全部有落点）

### 2.1 音频线程（**【实测】** + **【事实】**）

| 项 | v2.9.0 | v3.0.0 | 依据 |
|---|---|---|---|
| 每样本乘加 | 低频低通 1 次 + 平方累加 | **两个**低通（+1 乘加）+ **4 路**平方累加（full/low/mid/high）+ 子帧多 2 次加法 | `AudioFeatureExtractor.process` |
| 每样本 flop | ≈8 | ≈17 | `ref-research/audio-feature-extraction.md` §5 |
| 每次回调分配 | 0 | **0**（状态在 `configure` 时分配一次） | `filterState` / `baselineState` |
| 每次回调的额外回调 | 1（onBar） | 3（onBar + onFeatures + 条件性 onTransient） | `TransparentWaveformSink.handleBuffer` |

**实测（仪器探针 `PROBE-FEATURE-COST`，4096 帧立体声 × 4000 次）**：

| 设备 | 每次 process | 覆盖的音频时长 | 实时倍率 |
|---|---|---|---|
| **S6（Android 7.0，最慢的验收机）** | **574 µs** | 92.88 ms | **162×** |
| PCL110（Android 16） | 415 µs | 92.88 ms | 224× |

⇒ 纯算术上有两个数量级的余量。**风险不在吞吐**（`ref-research/audio-feature-extraction.md` §5 的结论一致），
而在**分配 / 阻塞 / 异常** —— 那三样是本版逐条守住的东西（见 `probe-audio-features.md` §4）。

**【未验证】**：真机播放下的欠载率（`dumpsys media.audio_flinger` 的 underrun 计数）未采集。

### 2.2 帧路径（GPU / 绘制笔数，**【估算】**，来自代码算式）

| 档 | v3.0.0 每帧新增的**绘制笔数** | 说明 |
|---|---|---|
| **简洁** | **0** | 与 v2.9.0 简洁档完全一致（背景模糊 + 呼吸，帧路径只有一次图层属性更新） |
| **精致** | **≤ 1 实心渐晕 + ≤ 1 描边圆 + ≤ 26 实心圆** | 冲击波（`SHOCK_CAPACITY = 2`，稳态常见 0~1）+ 光晕（`HALO_CAPACITY = 4`，精致 1 圈/次）+ 粒子（低密度 10/s × 0.9s ≈ 9 稳态，上限 40）。**逐柱着色是 0 笔新增**（每根柱子仍然只画一笔，只是那一笔的颜色跟着音频走） |
| **炫技** | **≤ 2 + ≤ 4 + ≤ 40 + 3 条能量条** | 高密度粒子（26/s × 0.9s ≈ 24 稳态）+ 光晕 2 圈/次 + 三条 `drawRect` 频带能量条 |

对照 v2.9.0 的预算（`docs/verification/v2.9.0/probe-perf-budget.md` §2/§3/§4）：
- v2.9.0 精致档的**波形本身**每帧已 ≤84 笔绘制（28 柱 + 28 峰值 + 28 光点）；
- v2.9.0 炫技档的 C 档是「≤32 个 `drawCircle` + ≤2 个描边圆」。
- ⇒ v3.0.0 **精致档把 v2.9.0 炫技档的 C 档预算搬到了精致档**（这是任务书 §4.4 的要求），
  但**粒子/光晕的容量与 v2.9.0 的 C 档同量级**（40 vs 32、4 vs 2），
  峰值绘制笔数从「≤34」涨到「≤46 + 3」。

**零分配的三条保证**（**【事实】**）：
1. 粒子/光晕/冲击波全部是**定长 SoA `FloatArray`**，构造时分配一次；
2. 径向渐变 `Brush` **缓存**（`RadialGradientCache`，按颜色 + 半径）—— 绝不在 draw lambda 里新建；
3. 逐柱着色用 `Color`（value class）的 `lerp`，**不分配**。

### 2.3 设置页（**【事实】**）

新增 5 个开关行 ⇒ 播放与音质二级页从 7 行涨到 12 行（`SettingsRenderPlanTest` 的计数断言同步更新）。
设置页是**按需组合**的页面，与帧路径无关。

## 3. 降级策略：**v3.0.0 已取消自动降级**（用户明确要求）

v2.9.0 的四级阶梯（砍 B → 砍 A → 波形降档，并**改写 `motion_tier`**）在 v3.0.0 **整个删除**。
理由（现场 + 工程判断）：

- 判据（60 帧窗口内 40% 超标）**不知道是谁把帧顶起来的**（归因要 Perfetto）；
  S6 上「完全关掉波形」的对照轮同样 95% 超标 ⇒ 砍掉的动效往往不是肇事者；
- 它会**改写 `motion_tier`**，于是设置页显示的档位与用户点的那一档不再一致；
- 最要命的是**渲染结果不再可推导**：「为什么这台机器少一层特效」在代码里找不到答案。

**性能兜底改由用户可见、可预期的手段承担**：

| 手段 | 说明 |
|---|---|
| ① 低端设备的**初始档位** | 静态判据（低内存 / 3.5GiB 级 / API<26）解析；**只在用户没选过时生效**，永不覆盖用户选择 |
| ② 五个**独立开关** | 用户想省电可以逐项关（关掉粒子 = 少 ≤40 笔/帧） |
| ③ 每个动效**自身**的硬上界 | 池容量 / 寿命 / 冷却 / 每帧生成上限 —— 机器慢不会让特效失控 |
| ④ 帧率上限（v2.8.0 遗留，未改） | `visualizerFrameIntervalMs`：API<26 或低内存 ⇒ 33ms（30fps），否则 16ms（60fps） |

**结构性保证**：`MotionEffects` 上**没有**降级水位字段（反射断言
`MotionEffectsTest.能力位对象上不存在降级水位字段`），`MotionPrefs` 上**没有**推进水位的入口
（`MotionPrefsTest.不存在任何推进降级水位的公开入口`）。

## 4. 帧监控：复用还是新建？

- `FrameBudgetPolicy`（60 帧窗口 / 16.67ms 预算 / 40% 超标）与
  `VisualizerFrameMonitor`（`Window.addOnFrameMetricsAvailableListener`，API 24+）**保留为诊断工具**，
  但**没有任何生产调用点** —— `MotionClock` 里的注册点已随机制一起删除。
- 帧时间测量改用**外部工具**：`dumpsys gfxinfo`（与 v2.6.2 / v2.8.0 / v2.9.0 同方法同口径），
  见 `../verification/`。
- 为什么不用 `withFrameNanos` 的 delta 当帧时长：Compose 的 `MonotonicFrameClock` KDoc 原文
  「may be normalized to the target time for the frame, not necessarily a direct "now" value」，
  与本仓库记录的 S6 流水线式掉帧（帧回调仍 60Hz、每帧晚 ~19ms）一致。
  见 `ref-research/compose-particle-systems.md` §3。

## 5. 未验证项

1. **S6 / PCL110 / WGR-W09 的 v3.0.0 帧时间**：见 `../verification/`（本探针阶段不驱动真机；
   真机数据在实现完成后用 **release 包**采集）。
2. **逐柱着色的实际 GPU 代价**：它**不增加绘制笔数**，但每根柱子换了一次画笔颜色
   （28 次 `drawRoundRect(color=…)` 的 paint 颜色写入）。**【未验证】**这一项在 S6 上是否真的免费。
3. **浅色主题下的观感与对比度**未复核。
4. **音频线程欠载率**未采集（见 §2.1）。
5. **取消自动降级之后，S6 在炫技档下是否仍然可用**：这是本版性能上最大的**风险点** ——
   v2.9.0 的阶梯曾把 S6 的动效砍掉过，现在不砍了。帧时间数据（`../verification/`）是唯一判据。
