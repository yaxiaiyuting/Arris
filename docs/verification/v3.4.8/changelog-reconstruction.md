### v2.1.5

- date: 2026-09-25
- source: `AGENTS.md` 的 `## v2.1.5 新增（本 fork · 跨源切歌歌词串台专项）` 小节
- concise: 修跨源自动切歌歌词串台：取词问错平台；当前播放身份收敛成单一写入点
- detail: 报障是「QQ 播完自动切到 ncm，音频已变但歌词还是 QQ 那首」，根因不是「旧歌词没清」而是**取词问错了平台**：自动接续那条路只更新了 `songId`，「当前歌属于哪个音源」还停在上一首，于是拿上一首 QQ 曲目的 songmid 去问 QQ，拿回来的自然是上一首的词，而且它通过了当时所有防串台闸门（那确实是「当前代」的响应）。结构性修法四条：①「当前播放的是谁」只能有一个写入点 —— v2.1.4 之前是三个并列 `var`（`currentSongSourceKey` / `currentSongSourceId` / `currentSongMediaId`）而只有 `playSong()` 会写，本版收成一个 `currentTrack: TrackKey?`，三个旧名字退化成只读派生值；② 路由依据必须是参数 —— `fetchLyrics(songId)` 按全局字段分支（`if (currentSongSourceKey == "qqmusic")`）改成 `fetchLyrics(track: TrackKey)`，问错平台在物理上不可能；③ `TrackKey` 的相等性只看 `(source, id)`，不含 `sourceId` / `mediaId`（那两个是取链载荷不是身份，算进去会把同一首歌在不同路径上判成「切歌了」）；④ 媒体项 mediaId 必须过 `SourceIds.mediaId(source, id)` —— v1.5.2 的 transition 守卫只比裸 id，所以 QQ 的预载项永远过不了守卫（gapless 静默失效）。真机才暴露两个坑：**去重与世代互相锁死**（`MainActivity` 的切歌回调会再调 `fetchLyricsForSong(当前 id)` 并无条件 `onTrackChanged` 让世代前进、作废在途请求，同时 `fetchLyrics` 的按曲目去重又挡掉重发 ⇒ 两边都不干活；修法是去重判据加上「那次请求仍是当前世代」，且 `fetchLyricsForSong` 对同一首歌不作废在途请求并原样沿用现有身份），以及 `catch (e: Exception)` **吃掉 `CancellationException`**（真机日志实证 `playJob?.cancel()` 后打出 `JobCancellationException` 被报成故障，取消必须原样抛出）。媒体面板（P1）的结论是「能力边界」不是 bug：应用已经**把当前歌词行发布到 `METADATA_KEY_TITLE`**（v1.6.0 的用户约定），华为 SystemUI 的 `MediaDataManager` 确实消费了它（`dumpsys` 里能看到 `song=<歌词行>`），但平台上不存在专门的歌词 metadata key（华为 SystemUI.apk、`MediaMetadataCompat` 1.7.0、media3-common 1.5.0 三处键集扫描均 0 命中，media3 1.5.0 也没有 `setLyrics()`），控制中心卡片肉眼是否显示、是否实时 **adb 无法判定**，本版刻意不动 v2.0.2 刚稳定的通知重 post 路径。dex 指标：release 产物（R8 minify）**单 dex、29,369 个方法、`max registers_size = 248`、0 个方法超 255**；debug 产物 24 dex、**11 个方法超 255**（`registers_size` 最高 500，集中在 i18n 那个约 165 属性的 `Strings` data class 与 `PlayerCard`）；「`registers_size = 500` ⇒ ART 必然验证失败」被实测反驳（那份 debug 构建就在 SM-G9209 / Android 7.0 上跑完了整条跨源切歌验证）⇒ **>255 计数 = 0 是健康信号，不是硬门槛**。未验证项：华为控制中心的屏幕侧结论、真机跨源连切 20 次没跑成（真机完成的是一次完整的 QQ → ncm 自然完播接续，A/B 各一次）、反向（ncm → QQ）真机 A/B 未做、API 24 上 `dumpsys media_session` 里没有 Ncrust 会话、release 包没有在 Android 7.0 / API 24 上装过。

- concise: 修波形尖端「变圆再变尖」：相位从插值取值改成几何平移（峰尖度波动 90%→0%）
- detail: patch 版、只修一个 P0，versionCode **63**，全量单测 **2556 用例 / 0 失败 / 192 个测试类**；用户反馈「波形条会**尖端变平滑再变回去**」并确认「就是 v3.4.0」—— 发布说明明确这一条 v3.4.0 **确实没修**，它修的是另一条（横向顿-冲），两者是**独立缺陷**。根因是**相位被用错了地方**：旧写法 `val v = window[i] + (window[i + 1] - window[i]) * phase` 看起来像「在相邻两格之间平滑滚动」，但它在数学上是**把两个相邻时刻的信号线性混合** —— **时域模糊，不是平移**；相位描述的是**位置**，却被拿去插**取值**。同口径实测（一段带尖峰的幅度、扫 12 个相位，判据 = 峰尖度）：值插值（旧）在相位 0.167 / 0.250 / 0.667 / 0.750 处分别给出 **0.0068 / 0.0034 / 0.0337 / 0.0339**（相位 0.000 的基准是 0.0191），**波动 90%**，摆动周期正好是柱间隔（约 100ms）—— 那就是用户看到的「尖端变圆、再变尖」；几何平移（新）在所有相位恒为 0.0191，**波动 0%**。修法：取值**直接取整格**（形状完全保真，不做任何时域混合），亚格相位交给 **x 平移** —— 复用渲染层早就有的 `xShift` 参数（渐变色流动用的就是它），x 范围多延伸一格补上左移露出的缺口，**不需要多采历史**；用户最初的提议「只在左右两端做平滑、中间写死」被实测否决 —— 那会让画面退回 **10Hz 整格跳变**，抖动率从 **57.8% 升到 166.9%**、单帧跳变 **100px**，比现状更抖，本修法**同时**做到形状保真与平滑滑动（逐帧位移仍是 0.167 格 ≈ 16.7px）。新增长期守卫：`位置平移的峰尖度不随相位变化`（要求波动 = 0%）与 `值插值确实会让峰尖度随相位摆动`（要求 > 30%）互为对照 —— 若有人把生产路径改回值插值，第一条会红，第二条记录「为什么不能改回去」。与 v3.4.0 那条的区别（发布说明专门列了对照表，避免混淆）：v3.4.0 修的现象是「画面顿一下再冲一下」、层次是**位移**、根因是「柱间隔在 UI 消费处倒推、被 vsync 量化 ⇒ 永不收敛 ⇒ 相位撞上限幅停住」；本条修的现象是「尖端变圆再变尖」、层次是**形状**、根因是「相位拿去插取值 ⇒ 时域模糊」，两者都会表现为「抖」但机制与修法完全不同。验证：API 33 模拟器 release 包装机**冷启 815 ms**、无崩溃，实际播放一首歌后波形绘制失败计数（`droppedCurveFrames`）为 **0**。**未验证**：**没有做视觉确认**（量的是 `heights[]` 与位移序列，不是看画面，最终仍需肉眼 smoke test —— 作者自述「我在这块组件上已经错过 6 次」，所以不把「仿真/单测绿灯」当成「你看到的抖动消失了」）；120Hz 未验证（环境没有高刷设备，模拟器 `fps=60.000004`，新公式里不存在与刷新率挂钩的阈值但这是推理不是实测）；模拟器用 SwiftShader 软件渲染、其帧时间不可作为真机结论。
