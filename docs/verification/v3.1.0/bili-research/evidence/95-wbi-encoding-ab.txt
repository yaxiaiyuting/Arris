[附] 编码问题的**结论性证据**（来自参考文档自身的多语言 Demo 对照）
================================================================================
来源：bilibili-API-collect docs/misc/sign/wbi.md（经存档 fork 取得）

| Demo 语言 | 实际调用                                        | 空格编码 |
|-----------|-------------------------------------------------|----------|
| 正文示例  | （散文里明确写出）                              | **%20**  |
| JavaScript| `encodeURIComponent(...)`                       | **%20**  |
| Python    | `urllib.parse.urlencode(params)`（= quote_plus）| `+`      |
| Golang    | `url.Values{}.Encode()`（= QueryEscape）        | `+`      |
| C#        | `new FormUrlEncodedContent(...)`                | `+`      |

⇒ **文档自相矛盾**：正文示例与 JS Demo 用 `%20`，Python/Go/C# Demo 用 `+`。
⇒ **JS Demo 是最有权威性的一份** —— 这些 Demo 是从 B 站自家前端逆向出来的，
   而服务端**必须**接受自家前端发出的编码。
⇒ `!'()*` 五个字符在编码前已被剔除，所以 `%20` vs `+` 的差异只体现在
   **空格** 与 **`~`**（Java 的 URLEncoder 把 `~` 编成 `%7E`，JS 的 encodeURIComponent 保留 `~`）。

[附2] 为什么**没能**用实测一锤定音
--------------------------------------------------------------------------------
尝试过的判别性实验（均失败，诚实记录）：

1. 在会验签的 `view/detail` 上**追加一个自定义含空格参数** `t=a b`：
   - `%20` 编码 → `code:-352`；`+` 编码 → `code:-352`
   - ⇒ 服务端**只对已知参数**计算签名，追加未知参数一律 -352，无法判别。

2. 在**已知参数 bvid 的值里**塞空格（`bvid=BV1GJ411x7h7 x`）：
   - `%20` → -352；`+` → -352；**连完全合法的 bvid 也变成 -352**
   - ⇒ 此时 `view/detail` 已对本机出口**整体风控**（见附3），实验作废。

3. 在**唯一**会用到含空格关键词的端点 `search/type` 上判别：
   - 不可能 —— 该端点在本机出口**根本不校验 w_rid**（无签名/伪造签名/正确签名结果全一致）。

⇒ **结论：在本次调研的网络条件下，`%20` 与 `+` 无法通过实测区分。**
   两者都能让空格解码为空格，最可能的服务端实现是「解析 query 成 map 后按自己的规则
   重新序列化」，因此**两种编码大概率都被接受**。归入未验证项。

[附3] ⚠️ 风控会**随时间升级** —— 同一个 A/B 在 18 分钟后失效
--------------------------------------------------------------------------------
2026-09-28 02:29:37  `view/detail` 无签名 → -352；**有签名 → code:0（OK）**   ← A/B 成立
2026-09-28 02:46:54  同一份代码、同一个出口：
    SIGNED   bvid=BV1GJ411x7h7&wts=1790534814&w_rid=<正确>  → {"code":-352,"message":"风控校验失败"}
    UNSIGNED bvid=BV1GJ411x7h7                              → {"code":-352,"message":"风控校验失败"}
⇒ **签名不再能救回来** —— 该端点对本机出口进入了整体风控状态。

同一时刻的对照（三个端点同时打）：
    search/type  无签名 : {"code":0,"message":"OK","ttl":1,...}          ← 仍然可用
    song/info au39      : {"code":0,"data":{"id":39,...}}                ← 完全不受影响
    song/url  au39      : {"code":0,"data":{"sid":39,...,"timeout":10800...}} ← 完全不受影响

⇒ **三条工程结论**（写进 RECOMMENDATIONS.md）：
  1. **音频区端点（`song/*`、`menu/*`）不参与 wbi 风控，是稳定的那条路**；
  2. **wbi / 视频端点会被风控降级**，且降级后签名也无效 ⇒ 必须有「降级到音频区」的退路；
  3. 这同时解释了为什么风控是「数次请求后」才出现的 —— 它是**按出口 IP 累积**的，
     开发期反复调试 wbi 端点会把自己的出口打进黑名单。**Ncrust 对 wbi 端点必须做速率限制与负缓存。**
