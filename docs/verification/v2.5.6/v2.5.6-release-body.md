## 1. 搜索：慢的那条腿不再拖住整屏

**以前**：搜索的规矩是「ncm 先回来才显示」。ncm 那条腿卡住时（真机抓到过 **30 秒**），
即使 QQ 的结果 5 秒前已到手，屏幕上也只有转圈。

**现在**：谁先回来谁先上屏，另一条到了再合并。状态行也诚实 ——
没回来的那一侧显示「搜索中…」而不是「0 首」。

真机数据（release 包 / PLC110 / n=4）：

| query | ncm 腿 | QQ 腿 | **首帧上屏（`ttfr`）** |
|---|---|---|---|
| `love` | 886ms | 2739ms | **888ms** |
| `jay` | 428ms | 3089ms | **429ms** |
| `piano` | 615ms | 1549ms | **616ms** |
| `hello` | 676ms | 4159ms | **677ms** |

`ttfr` P50 ≈ **646ms**。诚实标注：这 4 个样本里 ncm 都是先到的（4/4），
所以它们证明的是**健康路径没有回归**；「先到先发布」的收益只出现在 ncm 慢的异常路径上
（证据：探针抓到的 30s 空屏真机样本 + 本版回归复现时抓到的
`ncm 搜索中… · qm 30 首` 界面状态）。

### 1.1 本版自己造成并已修复的一次回归（公开留档）

给搜索加的 20s `callTimeout` 在真机上导致**ncm 恒 0 首**：该网络下每通请求
要 ~30 秒才把请求头送出去（`ttfb=240ms` 但 `total=30566ms` —— 慢在连接建立，不在服务端），
20s 的 `callTimeout` 于是拦掉了**本来会成功的请求**。**已删除**；
用户可见收益完全来自「先到先发布」，与超时无关。
复测：同一台设备 `ncm 30 首 · qm 30 首` ✅

教训：`callTimeout` 覆盖**整通**（含连接建立与排队），而 `connectTimeout`/`readTimeout`
是**分阶段空闲**超时 ——「ttfb 快」不代表「整通快」。

## 2. 平板：竖屏下 ⤢ 终于点得动（EMUI 真机验证）

**任务书前提被真机推翻**：EMUI **完全采纳**旋转请求
（`wm get-ignore-orientation-request=false`；应用持 `SENSOR_LANDSCAPE` 时强制
`user_rotation=0`，显示保持横屏 ≥10s；撤请求后立刻回竖屏）。平板横屏点 ⤢ 一直是好的。

**真因**：横向控制条是 `Box` + 三个各自 `align(CenterStart/Center/End)` 的 `Row`，
三组独立定位 ⇒ 竖屏 352dp 容器下左组（8–168dp）与传输组（103–247dp）**重叠 65dp**，
而 Compose 里**后声明的赢命中测试** ⇒ ⤢ 的槽位（128–168dp）**100% 被盖**，
点它触发的是**播放/暂停**（图标画得好好的，只是点不到）。
横屏 563dp 不重叠 ⇒ **只在竖屏出现**。

**修法**：改成**一条顺序 `Row`**（子节点结构上不可能重叠）+ 宽度预算让位规则
（左组含 ⤢ 与传输三键不可让，让的是音质片）。**没有**加任何 WindowManager 旋转 override。

**未验证**：大屏多窗口 / 华为 PC 模式下的方向采纳；应用内 `auto_rotate=on`（测试机为 off）。

## 4. baseline profile：管线已交付，产物未生成（诚实说明）

**探针推翻了三条前提**：仓库**有** `androidx.profileinstaller` 依赖（自 v1.2.1）；
APK 里**有** `baseline.prof`；S6（**API 24**）真机实测
`D ProfileInstaller: RESULT_INSTALL_SUCCESS` ⇒「API 24~30 永不安装」是假的。
v2.5.5 得出相反结论是因为它的取证命令**本身失败**（`aapt2` 少了 `--file`，
stdout 为空，而 `grep -c` 对空输入返回 0）—— 失败伪装成了阴性结果。

**真缺口是内容与管线**：`baseline-prof.txt` 是 91 行**手写 class-only 清单**，没有采样器。

**本版交付**：真机采样器（7 条旅程 + 逐条 OK/SKIP 日志）、一条命令重生成、
CI（自托管 runner + 手动/定期 + 开 PR）。

**本版未交付**：生成产物。`BaselineProfileRule` 有硬性 API 前提（实测报错原文）：
`requires API 33+, or a rooted device running API 28 or higher and rooted adb session`。
三台设备：S6（API 24，24<28）与 WGR-W09（API 31<33，且 `adb root` 在 production build 上被拒）
**结构性不可用**；PLC110（API 36）满足 API 但卡在
`UiAutomationService … already registered!`（关掉两个第三方无障碍服务、确认无残留
instrumentation、`adb reboot` 都试过，仍失败 ⇒ 修正了 v2.5.5 的根因判断）。
⇒ **不声称 profile 改善冷启动**；已量化的是**空间上界**：

| 编译档 | P50（API 24 / release / n=10） |
|---|---|
| `speed-profile`（按 profile 编译） | 598.5ms |
| `speed`（全量 AOT，不看 profile） | 500.0ms |

两者差 ~95–100ms（约 17%）= 方法级 profile 能争取的上界。
另：v2.5.6 的代码改动**没有让冷启动变慢**（B0−A = −8ms，噪声带内）。

   本版回归复现时的界面状态，不是受控 A/B。
5. **平板搜索延迟对照**未做（WGR-W09 无 `screenrecord`）。
6. **macrobenchmark 在本仓库至今没有一次成功运行**：本版实测 `StartupBenchmark`
   在 API 24 上挂死（`AndroidJUnitRunner` 打完 `Output Directory: …` 后 24 分钟零输出、
   进程 `S (sleeping)` 在 `SyS_epoll_wait`）⇒ 冷启动 A/B 改用平台命令，口径写进脚本。
7. **华为控制中心媒体卡片**：任务明令不碰 —— 全程未读取、未改动。

## 8. 本版新增的三条铁律（`AGENTS.md`）

20. **baseline profile 是启动性能的基础设施，不是可选优化**（内容 + 管线 + CI 三件都要）。
21. **平台特定行为必须在目标平台真机验证，不能只在模拟器上测**（本版靠它推翻了 EMUI 前提；
    并附带两条通用修法：优先顺序布局；命中区要断言「节点存在**且** bounds 不相交」——
    本例的图标画得好好的，只是点不到）。
22. **性能优化必须有量化数据支撑，无数据不声称优化**（含配套条款：
    任何「计数为 0」的结论必须同时留 stderr 与退出码 —— v2.5.5 那条假结论就是这么来的）。
