# Ncrust v3.2.4-gpl 更新说明（用户可读）

> `versionCode = 59` / `versionName = 3.2.4-gpl`
> 基线：`v3.2.3-gpl`（versionCode 58）

## 修好了什么

### 1. B 站的歌现在能放了（P0）

**症状**：上一版把 B 站音源接进来了，搜索、歌词都正常，**但点播放就是不出声** ——
要么一直转圈缓冲，要么直接报错。日志里看不出问题（取链成功、URL 也拿到了）。

**根因**：B 站的音频服务器对每一条取音频的请求要**同时**验两样东西：`Referer` 必须是 B 站的域名，
`User-Agent` 必须存在、而且**不能带「android」字样**。
上一版只补了第一样。而播放器默认发出的 User-Agent 恰好是安卓系统的默认值
（`Dalvik/2.1.0 (Linux; U; Android 13; …)`）——**一句话里同时踩了两个雷**，服务器直接 403。

**修法**：取音频时用一个**实测能过**的身份（与取链接口同一个桌面浏览器 UA），
并且**只对 B 站的地址生效** —— ncm 和 qm 的请求一个字节都没改。

**顺带修的**：有些 B 站歌曲的音频放在与 B 站无关的第三方 CDN 域名上，
上一版的「域名白名单」认不出它们，这一版改成「白名单 ∪ 本次取链实际拿到过的域名」。

**实测**：同一台设备、同一条链接、只改这一个头 —— 修复前 **403**，修复后 **206 + 真实音频字节**；
release 包上实际播放 B 站歌曲，播放状态 `PLAYING`、进度正常推进。

### 2. 新手机（高刷新率屏）上音频条不再抖（P1）

**症状**：在 120Hz 的新手机上，播放器里的音频条（三条频带波形）**一抖一抖的**；
老的 60Hz 手机反而很顺。

**根因**：波形的重绘节拍被**写死成 16 毫秒**，从来没有读过屏幕刷新率。
这个 16ms 在两种屏幕上含义完全不同：

- **60Hz**：屏幕每 16.67ms 出一帧，16ms 的节拍**每一帧都能满足** ⇒ 每帧都推进，没有抖动；
- **120Hz**：屏幕每 8.33ms 出一帧，16ms 的节拍变成「**每两帧才推进一次**」，
  而 16ms 与两帧的 16.67ms 只差 0.67ms —— 只要有一帧稍微晚一点，就变成「三帧才推进一次」（25ms）。
  于是音频条的移动量在 **16.7ms 与 25ms 之间反复跳**（单帧位移差 **+49%**），看起来就是抖。

**修法**：不再数时间，改成**数帧** + **读真实刷新率**：

- 普通手机：**每一帧都推进**（节拍器交给屏幕自己，60/90/120/144Hz 自动对齐）；
- 低内存老手机：仍然节流到约 30fps（`每 ceil(33ms/帧长)` 帧推进一次），这条老承诺没变；
- 屏幕刷新率变化时（面板在 60/120Hz 之间切换、LTPO 变频）会自动跟上。

**实测**：同一份判据在 60/90/120/144Hz 四档上的确定性测试，
120Hz 的「单帧位移离散度」从 **0.125 降到 0.042**（约 1/3），且**不再出现 25ms 的跳变帧**；
60Hz 上**新旧判据逐帧完全等价**（推进时刻逐个相等）—— 老设备零回归。

## 没有改什么

- 不改包名、不改签名、不动华为/荣耀的媒体控制卡片。
- 不新增任何设置项，不新增任何持久化字段（升级不会丢登录态、队列与离线缓存）。
- ncm / qm 的取流路径**逐字节未改**（只有 B 站媒体会带那两个头）。
- 音频特征提取、歌词、队列、预载槽位不变量一行未动。

## 已知问题 / 本次没验证到的（如实）

- **高刷新率真机上的观感没有实测**：本次开发环境里只有 60Hz 的模拟器，
  120Hz 那一侧的结论来自四档刷新率的确定性测试，不是真机观感。
- **老机器 S6（Android 7.0）没有实测**：本轮该设备不在线，用「60Hz 新旧判据逐帧等价」的单测代偿。
- **B 站登录态**下播放没有验证（没有 B 站账号；B 站音源也不在登录列表里，匿名即可播 320K）。
- 模拟器上的帧时间数字不具代表性（软件渲染），已在证据里标注。

## 怎么用

设置 → 音源 → 打开「B 站」，然后在搜索页搜关键词（或直接输入 `au数字` / B 站音频链接）。
B 站的歌与 ncm、qm 可以混在同一个队列里播放。
