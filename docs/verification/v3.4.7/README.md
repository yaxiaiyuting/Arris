# v3.4.7 验证证据

本版改的是**相位的时间基准**，不是参数。所以证据分三层：**判据单测**（能不能守住）、
**同一把尺子下的改前/改后**（量到了什么）、**真机探针**（假设成不成立）。

| 文件 | 是什么 |
|---|---|
| `ab-same-ruler.log` | 改前（`v3.4.6-gpl` 原样代码，git worktree）与改后（本版）跑**同一份脚本**的对照 |
| `probe-vsync-emu33.log` | 在 API 33 模拟器（1080×2340 / 60.000004Hz）上跑 `WaveformVsyncProbeTest` 的完整输出 |
| `probe-wiring-emu33.log` | **生产单例链路**（`WaveformStore.onBar` → `MotionClock.frame`）的端到端输出 |

## 一、判据（JVM，`app/src/test`）

| 用例 | 钉住什么 |
|---|---|
| `WaveformScrollPhaseAnchorTest.到达帧的位移必须是名义步长` | **用户点出的那条约束**：到达帧上相位 = 「这一帧比那根柱晚了多少」÷ 柱间隔，本来就该是个小正数；把它弄成 0 就等于把这一帧的位移丢掉 |
| `WaveformScrollPhaseAnchorTest.相位恰好等于 帧时间戳减最后一根柱的到达时刻 除以柱间隔` | 相位是**闭式**，不是「差不多」—— 逐帧等号（容差 1e-6） |
| `WaveformScrollPhaseAnchorTest.相位不来自任何累加时钟 —— dt 放大三倍相位逐帧不变` | 只要相位里含**任何**累加量（`dt` 或 `dt.toLong()`），这一条立刻翻红 |
| `WaveformScrollPhaseAnchorTest.旧模型在同一份时间线上会把到达帧的位移丢掉（特征化）` | 区分度自证：同一份时间线上旧模型量到 <50% 名义，新模型 ≥50% |
| `WaveformFrameRateTest.相位在一个柱周期内爬满一格` | 顶棚停留 0 帧（旧口径是 200/1200）、回绕不抖动 |

## 二、改前 / 改后（同一把尺子）

尺子只有一条，就是渲染层真正消费的两个量：

```
每帧可见位移 = Δ(窗口平移格) + Δ(scrollPhase01())
```

时间线：帧按标注刷新率均匀、柱按标注间隔均匀且**不在帧网格上**。脚本逐字相同，
改前跑在 `git worktree add v3.4.6-gpl` 的**原样代码**上（不是我在测试里复刻的旧模型）。

| 场景 | 改前抖动率 | 改后抖动率 | 改前顿帧 | 改后顿帧 | 改前到达帧位移 | 改后到达帧位移 |
|---|---|---|---|---|---|---|
| 146.2Hz / 82.6ms（屏幕录像量到的真机工况） | 8.01% | **6.52%** | 5 | **0** | **0% ~ 113%** | 73% ~ 118% |
| 120Hz / 41.2ms（用户报告的那台） | 10.60% | **6.63%** | 0 | **0** | 92% ~ 200% | 82% ~ 120% |
| 60Hz / 100ms（S6 形态） | 9.13% | **2.83%** | 1 | **0** | **0% ~ 200%** | **96% ~ 102%** |

读法：**「到达帧位移 0%」就是用户报的那条** —— 相位被锚点覆盖回 0，这一帧的位移整份丢掉，
下一帧再补回来（用户原话：「相位每 5 帧走 0.206×5，第 6 帧被覆盖回 0」）。
改后它回到名义步长附近（96%~102% @60Hz），抖动率同时降到 1/3。

## 三、真机探针（API 33 模拟器 · 1080×2340 · 60.000004Hz）

探针做了三件与生产同构的事：柱由**独立线程**按自己的节拍 push、时间戳取
`SystemClock.uptimeMillis()`；帧用 **Choreographer 的真实 vsync**；相位/平移按上面的尺子量。

| 臂 | 柱 100.0ms | 柱 82.6ms | 柱 41.2ms |
|---|---|---|---|
| 同源（帧时间戳喂给 ring，本版生产路径）抖动率 | **3.30%** | **3.16%** | **3.34%** |
| 同源到达帧位移 | 96%~109% | 89%~108% | 88%~108% |
| 同源顿帧 / 倒退 | 0 / 0 | 0 / 0 | 0 / 0 |
| 累加（环按 `dt` 自己攒时钟）抖动率 | 9.08% | 3.27% | — |

**最关键的一条假设验证**：同一帧里 `SystemClock.uptimeMillis()` 与
`frameTimeNanos / 1e6` 的差实测 **均 0.0~0.1ms、最大 1ms** ——
两个时间戳确实是**同一个单调时钟基准**（差值就是回调延迟）。
相位锚点把这两个量相减，这条是前提；它现在有数。

## 三·补、生产单例链路（端到端）

`WaveformRing` 的单测只能证明「喂它 `nowMs` 时算得对」，它在设备上真正跑的是
`onBar`（音频线程，自己打 `uptimeMillis()`）→ `MotionClock.frame(nowMs=…)` → `WaveformStore.pump`
→ `ring.pump`。这条链上任何一处漏传 / 传错单位，单测都会全绿而设备上照旧抽搐。

`WaveformPhaseWiringProbeTest` 用**一个明显不对的 `dt`** 把两套口径分开（`dt = 200ms`，
而柱间隔实测 ≈ 80ms）：

```
WIRING 第一帧: elapsed=0ms  dt=200ms phase=0.0000   ← 累加口径在这里会是 1.0
WIRING 第二帧: elapsed=31ms dt=200ms phase=0.3875   ← 31 / 0.3875 = 80ms = 实测柱间隔
```

两帧的 `dt` 都是 200ms，相位却只随**真实时间戳**走 ⇒ 生产链路上锚点确实生效，
没有退化成累加口径。

## 四、没验证到的（如实）

1. **没有真机**：本轮开工时原设备已从 `adb devices` 消失（用户明确告知真机不可用），
   所有探针数据来自 **API 33 模拟器**。模拟器的 vsync 是合成的、`dt` 实测 sd=0.000ms，
   所以「帧时间抖动下相位是否仍然匀速」这一条**只有 JVM 仿真的支持**，没有真机证据。
2. **没有肉眼观感验证**：本环境无法渲染这条波形（它只在横屏大屏 / 平板宽屏挂载）。
   「抽搐是否消失」最终要靠用户的眼睛。
3. **release 包没有做帧时间测量**（铁律 16）：本版改的是纯逻辑，没有新增逐帧分配与绘制，
   但**没有** release 包上的实测帧时间。
