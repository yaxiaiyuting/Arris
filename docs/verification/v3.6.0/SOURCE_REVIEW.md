审查基线：`2414a7c`。按用户要求，在彩蛋修正版构建期间抽查 QQ 续期与取链、播放上报、队列身份决策、歌单写入门控和应用内更新。以下三项是由生产调用链确认的待修复问题；本报告不声称完成全仓库审计，也没有用真实账号或手机复现。它们尚未改入本轮生日功能包。

## 1. [P2] 并发续期成功仍可能向本次取链返回旧凭证失败

位置：`app/src/main/java/com/takahashirinta/ncrust/qq/QqTokenRefresher.kt:273`，调用处 `qq/QqApi.kt:389`、`:402-405`。

`refresh()` 遇到正在执行的刷新直接返回 `SKIPPED_IN_FLIGHT`。取链前收到这个结果后仍继续用当前 cookie 发请求；取链被拒后，重试入口又只接受 `REFRESHED`。典型顺序：后台刷新 A 在飞 → 播放请求 B 的 preflight 被跳过 → B 用旧票发取链 → A 成功换新票 → B 收到旧票拒绝 → B 的被动刷新返回 `SKIPPED_RECENT_SUCCESS` → `QqApi` 原样返回旧失败。若 A 还没完成则返回 `SKIPPED_IN_FLIGHT`，同样没有等待/重试。

影响：本地凭证已经能够恢复，但到期窗口里的首次播放仍可显示需要登录或取链失败。它可能解释部分到期后的播放失败，不能据此认定此前「一周后掉登录」的唯一根因。

建议：对同一会话共享在飞结果；取链在凭证版本变化或刚完成刷新后，用新票重试一次。继续保留失败冷却、会话版本门控和有界重试，不新增刷新风暴。回归应通过可控 Deferred 把以上两种响应顺序固定下来。

## 2. [P2] 播放上报把播放位置当作实际收听时长

位置：`app/src/main/java/com/takahashirinta/ncrust/ui/viewmodel/PlayerViewModel.kt:671-675`、`:697-699`；字段定义见 `player/PlayReporter.kt:65` 附近。

`onProgressUpdate` 以 `pos / dur >= 0.8` 判定完成，并把 `pos` 传进约定为实际播放毫秒数的 `playedMs`；自然结束路径则直接传整曲 `duration`。`PlaybackService.seekTo` 和暂停状态的定位回调也会更新进度，因此拖到末尾或从靠近结尾的记忆位置恢复，即使只播放很短时间，也会发出数分钟的 `time`。例如 240 秒歌曲拖到 210 秒后，该代码会把 `time=210` 发给服务端；实际新增收听可能只有一两秒。

影响：收听上报和推荐输入不准确；问题并不证明服务端一定把该请求计入听歌排行。

建议：按播放会话累计真正处于 isPlaying 的单调时间，seek/恢复位置不能增加累计值；暂停、切歌、重播和自然结束分别结算。是否保留「80% 位置」作为触发策略可单独决定，发送的 time 至少应是实际收听时长。

## 3. [P2] 系统时间回拨会把歌单写操作挂起很久

位置：`app/src/main/java/com/takahashirinta/ncrust/network/PlaylistEditApi.kt:61-67`。

两次写操作的 2 秒间隔使用 `System.currentTimeMillis()`，并在持有全局 Mutex 时执行 `delay(wait)`。一次写入后若系统时钟向后调整一小时，下次计算为 `2000 - (-3600000) = 3602000ms`，本次及其后排队的创建、改名、增删歌操作都会等待约一小时。只切换时区不会改变 epoch 时间，本问题需要手动改时间、时间校准回拨等条件。

建议：进程内节流改用 `SystemClock.elapsedRealtime()`，把等待限定在 0..2000ms。QQ 的成功静默/失败冷却也使用墙上时间（`QqTokenRefresher.kt:517-548`），同类回拨会拉长窗口，后续修复应一起检查。
