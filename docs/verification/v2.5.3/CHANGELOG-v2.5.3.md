|---|---|
| `Strings` 拆成三个组（245 → 128 个构造参数） | **不能**。36 个消费文件、~290 个调用点一行未改；120 条文案逐值比对证明「搬家 ≠ 改文案」 |

**所以本版不声称修好了任何用户可见的问题。** 它买的是两件长期的事：

1. **`Strings` 从「一直是满的（余量 0）」变成「余量 121」** ——
   在此之前，每加一条文案都要先搬家一次（`240 → 261(崩) → 244 → 245 → 244 → 245`）；
2. **队列身份从「靠纪律」变成「靠类型」** ——
   跨源不再可能因 id 撞号被误判为同一首；判重逻辑第一次可被单测覆盖，
   并与待播槽位 / 歌词闸门 / 续播恢复收敛成**同一套**身份规则。

## P0 · `Strings` 拆分（主构造器 245 → 128）

### 为什么要做

`Strings` 是「一个 data class 装全部 UI 文案」的结构，而 dex 单方法只有 255 个参数寄存器：

```
槽位 = this(1) + N + ceil(N/32) 个默认值 mask + DefaultConstructorMarker(1) ≤ 255
N = 245 ⇒ 1 + 245 + 8 + 1 = 255   ← v2.3.0 ~ v2.5.2 的真实状态：**一个空位都没有**
N = 246 ⇒ 1 + 246 + 8 + 1 = 256   ← 溢出
```

溢出的表现是**编译照过、真机启动即崩**（`ClassFormatError` / `VerifyError`），
v2.0.0 · HF1 与 v2.3.0 各踩过一次。

### 做了什么

按**功能面**把 120 条搬进三个组（判据 = 消费文件，见 `docs/verification/v2.5.3/probe-strings.md`）：

| 新组 | 条数 | 功能面 |
|---|---|---|
| `SettingsStrings` | 64 | 设置页及其卫星（存储 / 背景 / 账户 / 电池 / 扫码入口） |
| `AboutStrings` | 25 | 关于页 |
| `PlayerUiStrings` | 31 | 播放器界面（传输控件 / 歌词页 / 队列面板） |

`245 − 120 + 3 = 128` 个参数 ⇒ **134 / 255 个 dex 槽，余量 0 → 121**。

**没有采用「按语言包拆」**：8 种语言里取值逐字相同的 key 只有 1 条
（`uidLabel`），语言维度根本不在外层构造参数里 —— 那样拆外层一个参数都少不了。

### 兼容性

老调用点 `strings.qualitySectionTitle` 这类写法**全部照旧可用**：
每搬一条都在 `Strings` 类体里留了一条同名转发属性
（`val qualitySectionTitle: String get() = settings.qualitySectionTitle`）。
转发属性不进构造函数，所以既不占 dex 槽，也不改变调用点。

新代码可以直接写 `strings.settings.qualitySectionTitle` 这种带分组的路径。

### 怎么保证 960 个字符串一个都没搬错

`Strings` 里有 47 条 lambda 文案，值就是格式串里的空格与标点 ——
**任何一次顺手的格式化都是静默的文案改动**，编译期完全看不出来。

做法：拆分**前**用反射把 8 种语言的**全部可达文案逐值导出**成黄金快照
（494 条路径 × 8 语言；lambda 用哨兵实参**实际调用一次**记下输出串），
拆分**后**再用同一套逻辑导出一次**逐值比对**。
`StringsMigrationTest` 在每次 `./gradlew test` 时都跑这 8 条用例。

## P1 · 队列去重改用 `TrackKey`

### 探针结论（先说清楚这不是修 bug）

| 问题 | 实测 |
|---|---|
| 跨源 `song.id` 冲突实际发生率 | **0** |
| 为什么是 0 | 全部 QQ id 经 `SourceIds.qqId()` 产出，**bit62 恒置位**（≈4.6e18）；ncm songId 是 1e6~3e9 量级 ⇒ 两段区间在 64 位整数上**不可能相交** |
| A/B 抽样 1000 首双源配对 | 裸 id 跨源冲突 0 次、同源重复 0 次 |
| 用户报障 | **一条都没有** |

本版顺带**更正**了 v2.5.0 / v2.5.1 遗留清单里「跨源裸 id 撞号会把其中一首当重复」的
说法 —— 那个前提需要两个平台的 id 落在同一数值空间，而它们不是。

### 改了什么

- 队列的取身份收敛到**唯一入口**：`SongItem.trackKeyOf()` / `QueueKeys.keyOf()`；
- 原先散在 `MainActivity` 里的 **14 处内联判重表达式**收敛成
  `player/QueueKeys.kt` 的纯函数（判重 / 重定位 / 批量剔除 / 重建 / 诊断）；
- `QueueInsert.plan` 的入参从 `List<Long>` + `Long` 换成 `List<TrackKey>` + `TrackKey` ——
  `plan(queue.map { it.id }, …)` 现在**编译不过**；
- `SongItem.dedupeKey`（v2.1.0 就定义好、带守卫测试、但生产代码零调用）
  **第一次真的接上了线**，取值 = `TrackKey.ofSong(this).tag`。

### 边界判据

| 情形 | 结果 |
|---|---|
| 同源同 id | **去重** |
| 跨源同 id | **不去重**（不同音源是两首歌） |
| 重复调用同一操作 | **幂等** |

### 行为不变的部分（已单测钉住）

- **队列顺序**：不变（就是 `List<SongItem>` 的顺序）；
- **待播槽位**：不变（它从 v1.5.2 起就按 mediaId 里的音源判定，本版没碰）；
- **随机模式**：不变（编排是**下标**，算法一行未动）；
- **续播进度**：不变。

### 历史数据

**不需要迁移。** 队列快照落盘的是 `List<SongItem>`（Gson 全量对象，不是 id 列表），
v2.1.0 起每条都带 `source` / `mid` / `media_id`，`TrackKey` 可直接从既有字段算出。
v2.1.0 之前的条目没有 `source`，按既有语义回落 ncm —— 那正是老数据的正确解释。

**升级不会丢队列、不会丢待播、不会丢续播位置。**

## 顺带发现但**未修**的问题（如实列出）

`SearchHistoryManager.HistoryItem` 只保存 `id`、没有 `source` 字段，
所以从**搜索历史**点播一首 QQ 曲目时，它会被当成 ncm 曲目
（`SongItem.musicSource` 回落 ncm）。

- 这是**既有**问题，不是本版引入的；
- 本版**没有修它** —— 完整修复要改历史记录的持久化结构 + 迁移 + 单测，超出本次范围；
- 但本版通过给队列身份选 `TrackKey.ofSong`（会看 id 里的 bit62 标志位）**避开了**它：
  即使 `source` 字符串丢了，队列也能认出这是 QQ 曲目。
- 列入下一版候选。
