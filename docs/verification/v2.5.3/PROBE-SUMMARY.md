## ① Strings 拆分方案：选型与理由

### 现状（探针实测，两种解析法互证）

```
Strings 主构造参数 : 245
dex 槽位           : this(1) + 245 + ceil(245/32)=8 mask + marker(1) = 255 / 上限 255
余量               : 0        ← 任务书说的「245/245 = 天花板」成立，且比字面更紧
嵌套组             : 7 个，合计 136 个参数，最大 SourceStrings(57)
类体转发属性       : 111 条（「搬家不改调用点」这套机制已被验证过四遍）
消费文件           : 36 个，全部在 ui/ + MainActivity
```

历史轨迹说明问题不是「快满了」而是「一直在满」：
`240 → 261（真机崩） → 244 → 245 → 244 → 245` —— 前四版全是「腾 2 花 1」。

### 三个方案的评估

| 方案 | 能否降低外层参数 | 迁移成本 | API 兼容 | 结论 |
|---|---|---|---|---|
| **A 按功能模块** | ✅ | 纯机械（有 111 条转发属性的先例） | ✅ 调用点零改动 | ✅ **采纳** |
| **B 按语言包** | ❌ **算术上不可能** | — | — | ❌ 否决 |
| **C 组合** | 同 A | 同 A | 同 A | 语言维没有可组合的东西 ⇒ 退化为 A |

**方案 B 为什么被否决（这是算术，不是偏好）**：语言维度**不在外层构造参数里** ——
`Strings` 的 245 个参数是「文案条目」，8 个语言文件各自提供一份实参。
按语言拆只会让「谁持有 8 份」换一个位置，外层参数一个都少不了。
探针另外给出一个佐证：**8 种语言里取值逐字相同的 key 只有 1 条（`uidLabel`）**，
即 8 个语言文件是 8 份实质不同的数据，不存在「可共享的语言包」。

### 采纳的分组（判据 = 消费文件，不发明新命名法）

| 组 | 条数 | 主要消费文件 | 净腾槽位 |
|---|---|---|---|
| `SettingsStrings` | 64 | `ui/screen/UserScreen.kt`（78 keys，是第二名的 2.7 倍）+ 其卫星 | +63 |
| `AboutStrings` | 25 | `ui/screen/AboutScreen.kt` | +24 |
| `PlayerUiStrings` | 31 | `ui/player/` 下的 PlayerCard / FullPlayerControls / LyricsView / QueueView | +30 |

**`245 − 120 + 3 = 128` 个参数 ⇒ `1 + 128 + 4 + 1 = 134` 槽，余量 0 → 121。**

为什么不拆得更碎：剩下的 146 条分散在 14 个详情页里（每页 11~29 条），
继续拆只会产生一堆 20 参数的小组、把类体撑得更长，而余量从 121 涨到 150+
**没有实际意义**（验收线是 <150）。
高频通用文案（`cancel`/`close`/`retry`/`loading`/`back`/`loadFailed` 等）
**一条都不动** —— 它们跨 8+ 个文件出现，「放哪个组」没有正确答案。

### 迁移方式与「搬家 ≠ 改文案」的证明

每搬一条，在 `Strings` 类体里补一条**同名转发属性** ⇒ **36 个消费文件、
~290 个调用点一行都没改**（与 v2.0.0 · HF1 给 `OfflineStrings` 的做法完全一致）。

搬运的正确性由**逐值快照**证明，不靠人眼 diff：`Strings` 里有 47 条 lambda 文案，
值就是格式串里的空格与标点，顺手的格式化就是静默的文案改动（编译期看不出来）。

1. 拆分**前**：反射导出 8 语言的**全部可达文案** → `strings-snapshot-v2.5.2.json`
   （494 条路径 × 8 语言；lambda 用哨兵实参 `❰s1❱` 实际调用一次记输出）；
2. 拆分（`split-strings.py`，对 v2.5.2 源码可重放出逐字节相同的结果）；
3. 拆分**后**：`StringsMigrationTest` 用同一套反射再导一次，**逐值比对**。

## ② 队列去重冲突：实际发生率

### 现状

队列去重用**裸 `song.id`**，落点 **14 处**，全部是 `MainActivity.kt` 里的内联表达式
（既不可单测，又是各自会漂移的一份口径）。

刺眼的既有事实：`SongItem.dedupeKey`（KDoc 写着「**队列内判重用的身份串**」）
**在生产代码里的调用点是 0 处** —— 阵地早修好了，只是没接线。
（v2.5.3 把它的**定义**并到与生产路径同一个落点上，使它不再会漂移；
但直接读它的代码仍是 0 处 —— 「不再漂移」≠「已被调用」。）

### 冲突发生率 = 0（**结构性**，不是抽样运气）

```
QQ_ID_FLAG = 1L shl 62 = 4611686018427387904
ncm songId 实测量级 : 1e6 ~ 3e9（远小于 2^40 = 1099511627776）
QQ 合成 id 最小值      : 4611686018427387905（bit62 恒置位）
两个区间相交           : 否
```

⇒ 只要 QQ 曲目的 id 都经 `SourceIds.qqId()` 产出，**「ncm id == QQ id」
在 64 位整数上不可能成立**，与队列长度、抽样规模都无关。

**A/B 对照抽样（1000 首双源配对，取值形状取自仓库里的真实观测）**：

| 指标 | 裸 `song.id` | `TrackKey` |
|---|---|---|
| 跨源数值冲突 | **0** | **0** |
| 同源重复 | 0 | 0 |

同源唯一性：ncm = 平台 songId（唯一）；QQ = `bit62 \| songid`（唯一）；
QQ 无 songid 时的 FNV-1a 散列兜底：抽样 20000 个 songmid → **0 碰撞**
（理论概率 `n²/2^63 ≈ 4.3e-11`）。

### 跨源冲突的实际影响 & 用户报障

- **今天的影响面 = 0**（因为上面的算术）；
- **没有找到任何一条用户报障**（`docs/**` + `AGENTS.md` + `git log` 全文检索）。

### ⚠️ 对既有遗留清单的更正

v2.5.0 / v2.5.1 的未验证清单写着「跨源裸 id 撞号时会把其中一首当重复」。
**这句话的前提在本版被证伪** —— 它需要两个平台的 id 落在同一数值空间。
按 `AGENTS.md` v2.5.1 规则 2（探针结论与既有说法冲突时以探针为准），本版更正它，
并把 TrackKey 改造**重新定性为结构加固，而不是 bug 修复**。
本版**不声称修好了任何用户可见的问题**。

## ③ TrackKey 改造影响面

| 机制 | 身份 | 改动 | 行为变化 |
|---|---|---|---|
| 队列**顺序** | 无（`List<SongItem>` 的顺序） | 无 | **不变** |
| 队列**去重** | 裸 `Long` → `TrackKey` | 14 处收敛进 `player/QueueKeys.kt` | 正常路径逐值不变 |
| **待播槽位** | `(source, id)`（编在 mediaId 里） | **没碰** | **不变**（新增「与队列身份一致」的断言） |
| **随机模式** | **下标**（`List<Int>`） | 只换入参类型，算法一行未动 | **不变**（新增跨源队列下的排列合法性用例） |
| 续播进度表 | 裸 `Long`（QQ 是合成 id） | 无 | **不变** |

**随机模式按下标**这一点是动手前必须确认的 —— 如果编排按身份存，改造面完全不同。

### 历史数据：**无需迁移**（已证明）

队列快照落盘的是 `List<SongItem>`（Gson 全量对象，**不是 id 列表**），
v2.1.0 · A 起每条都带 `source` / `mid` / `media_id` ⇒ `TrackKey` 可直接从既有字段算出。
v2.1.0 **之前**的条目没有 `source`，`MusicSource.fromKey(null)` 回落 ncm ——
那正是老数据的正确解释，本版**保持**该语义。

> **不写迁移逻辑**是正确决定：v1.9.3 的规则是「加字段 = 加迁移逻辑 = 加单测」，
> 而**本版没有加任何字段**。为不存在的旧形状写迁移只会引入一份需要长期维护的死代码。
> `QueueKeysTest` 用 4 条用例（老 JSON / 新 JSON / 混合队列 / 新旧判重键一致）钉住这一点。

### 顺带发现的相邻风险（**不是本版引入**，本版只避开它）

`SearchHistoryManager.HistoryItem` 只存 `id`、没有 `source` ⇒
搜索历史里恢复出来的 QQ 曲目会被 `SongItem.musicSource` 认成**ncm**。
这直接决定了 P1 用哪个构造函数：`TrackKey.fromSong`（字符串口径）会继承这个错误，
`TrackKey.ofSong`（走 `TrackKey.of`，`source` 为空时按 bit62 推断）不会。
**本版选了 `ofSong`** 并把它定为唯一落点。完整修复（改历史记录的表结构 + 迁移 + 单测）
**超出本次范围**，列入下一版候选。
