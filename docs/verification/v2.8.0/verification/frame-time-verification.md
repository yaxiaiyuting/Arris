> 本文件只记录**实测**数据与可复现命令，并如实标注每一处混淆因素。
> 原始 `dumpsys gfxinfo` 全文与逐次状态截图见同目录 `frame-*.txt` / `frame-*-state.png`。


## 4. 结论（如实，不美化）

1. **相对同法基线（第 1 行），v2.8.0 的三档都更贵**：P50 +5…+8 ms、P90 +2…+6 ms、P99 +11…+22 ms。
   即便最省的「简洁」档（第 3/6 行）也高于基线的 P50 15 ms。
   ⇒ **「同帧预算下不比 v2.6.2 贵」这个说法不成立，本版在 S6 上确实更贵。**
2. **但它不是「从满帧掉到卡顿」**：帧产出量（944 → 933–970 帧/30s）基本不变，
   P90 的差距（+2…+6 ms）与 P99 的差距（+11…+22 ms）都发生在**基线本身就已超出 16.7 ms 预算**的区间里
   —— S6 的旧波形 P50 也只有 15 ms（≈ 60 fps 里已经贴线）。
3. **会话间漂移不可忽视**：同一基线在两轮里 P50 差 4–5 ms（15 vs 19–20）。
   因此上面「+2…+6 ms」的一部分可能来自漂移；**能确定的只有方向**（新档位不低于旧实现），
   精确差值需要 bench harness（见 §6）。
4. **低端机默认档与自动降级都在真机上生效**（这是本版最重要的两条实测结论）：
   - S6 上不写任何 `visualizer_tier` 时，设置页显示 **简洁**（`visualizer_tier=0` 由
     `deviceDefaultTier` 解析得到；`prefs` 里**没有**写入该键 —— 已用 root 读回确认「不落盘」）；
   - PCL110（Android 16 / 15.7 GB）同一位置显示 **精致** ⇒ 平台判据 A/B 有效；
   - 测量过程中 App **真的自动降了一级**：root 读回 `visualizer_auto_downgraded=true`
     （`FrameBudgetPolicy`：60 帧滑窗内 ≥24 帧超 16.67 ms 即降，且每进程一次、降级后写回
     `visualizer_tier`）。S6 的 P50 本来就 ≈20 ms ⇒ 该阈值在 S6 上几乎必然触发。
5. **由此带来的两个副作用（必须写进 release note / 遗留风险）**：
   - 在 S6 这类设备上，用户手动选「精致/炫技」会被自动降回「简洁」，设置页显示的就是降级后的实际档位；
   - 因此 **第 4/5 行（T1/T2）的数据可能已被自动降级污染**（降级发生在那 30 s 窗口之内），
     它们应当被读作「T1/T2 的上界」，而不是纯净的 T1/T2 帧时间。

## 6. 未测 / 需补

- **PCL110（API 36）的波形帧时间**：见 `frame-pcl-*.txt`（若为空即未取到 —— 该机坐标尚未校准，
  不把未校验的数据写进来）。
- **音频线程侧开销**（`handleBuffer` 回调率、RMS 逐样本成本）：三段探针都标为未确认，
  本轮仍未测（需要 `atrace`/`perfetto` + 音频线程切片）。
- **真正的 bench harness**：`benchmark/` 里的 macrobenchmark 不覆盖可视化稳态
  （探针 §6.2 已指出），要拿到低噪声的档位差值需要新增一个 `WaveformBenchmark`
  （API 29+ 才能用 FrameTimingMetric ⇒ 只能在 PCL110 这类设备上跑）。
- 自动降级阈值（≥24/60 帧超预算）在低端机上的**产品合理性**未经用户验证：
  本版按任务书「性能不达标时自动降级」实现，但 S6 上等于「永远停在简洁档」。
