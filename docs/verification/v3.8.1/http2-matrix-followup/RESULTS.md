# 网易云播放网络异常：同设备协议与地址族对照

完成：2026-10-30T21:50:11.718727+09:00（Asia/Tokyo）。用户明确授权真机/同账号/只读取链实验。此次目标是解释反复失败，不继续凭错误文字归因或扩大业务改动。

## 结论

**本轮持续8秒超时的直接失败链已实测定位：当前Wi-Fi到DNS优先返回的网易云IPv6目标未完成TCP握手，而30秒单地址连接超时长于8秒整通截止；调用在尝试后面的IPv4地址前就被取消。**

这发生在TLS和HTTP协商之前。只改协议或加PING无法解决这个阶段的等待。IPv4控制下h2/h1均可正常获取播放地址；保留IPv6并只将单地址连接等待改为2秒，也观察到IPv6超时后改连IPv4成功。恢复原参数后再次失败，降低“刚好网络自行恢复”的混淆。

不能进一步把故障归到某一运营商路由器或网易云IPv6节点：缺少路径两端抓包/服务器日志。本轮也**没有重现历史REFUSED_STREAM/CANCEL**，不能把所有旧错误都用这一根因解释。

- 设备PLC110、API37；独立app_process以Arris UID10377运行，无应用覆盖安装、无歌曲播放。
- 同一曲25841325、jymaster、目标interface3.music.163.com/eapi/song/enhance/player/url/v1。每个矩阵启动时读取同一手机当前登录态并冻结，同一矩阵各协议条件共用完全同一份请求；矩阵之间重新读取本机快照，未记录凭证指纹，不声称跨矩阵Cookie逐字节不变。未触发登录或写操作。
- OkHttp4.12.0 / Okio3.9.1 / Kotlin1.9.24；单请求串行、间隔2秒，顺序轮换，3次/主要条件；15秒PING、30秒空闲池、8秒整通截止保持不变。默认连接恢复开启，所有尝试通过EventListener记录。
- 全部实验显式DIRECT；全局代理每组前后均为:0。未修改手机网络、IPv6、DNS或代理设置。TLS沿用系统默认验证，不加入抓包CA、不跳过证书/主机名验证。

## 四段对照结果

| 条件 | 只读请求数 | 可播响应数 | 结果 |
|---|---:|---:|---|
| 系统DNS顺序，单地址连接等待30s，整通8s | 12 | 0 | 均只尝试首个IPv6地址，未进入TLS，约8001–8003ms被整通截止取消 |
| 仅选择IPv4，其他配置保持 | 12 | 12 | 全新h2、真正复用h2、全新h1均200且可播 |
| 系统DNS顺序，仅连接阶段改为2s | 12 | 12 | 新连接先IPv6超时，再在同一Call里连IPv4成功；复用h2直接成功 |
| 恢复原系统DNS/30s配置，反向确认 | 2 | 0 | 全新h2、全新h1各一次，再次只尝试IPv6并8秒超时 |

合计38次只读取链，24次HTTP200且业务code200、可播，14次TLS前失败。不是将探针夹具断言或HTTP状态码直接当成成功：成功记录还验证了data[0].url非空，响应体与URL未落日志。

### 真正协商成功的协议矩阵（IPv4控制）

| 条件 | 3次耗时ms | 实际协议/连接 |
|---|---|---|
| 全新h2 | 325 / 286 / 2487 | 均h2，均新连接 |
| 复用h2 | 413 / 88 / 2362 | 均h2，reused=true、connection_id=1 |
| 全新h1 | 294 / 322 / 1674 | 均http/1.1，均新连接 |
| h2闲置约22秒后 | 92 | 同一connection_id=1，确认复用 |
| 随后闲置35秒 | 306 | 新connection_id=8；reused=false，空闲回收生效 |

样本用于定位失败层级，不据此宣称h1/h2哪个普遍更快。种子请求315ms也成功。

### 保留系统地址顺序的恢复证据

例：system-connect2.jsonl中fresh_h2/round1：

1. DNS返回IPv6 2409:8c6a:b021:1400:0:4:0:3，其后IPv4 117.135.207.67。
2. 第6ms开始连接IPv6；约2008ms连接阶段SocketTimeout。
3. 第2009ms改连IPv4；约2086ms进入TLS，2154ms协商h2。
4. 第2312ms完成HTTP200、业务200、取得可播地址。Call未被取消。

原参数下同一类请求只有第一个IPv6尝试，第8001ms整通截止，未尝试IPv4。恢复原参数后的两次确认同样失败。这是地址尝试和截止关系的直接记录，不是从ttfb=-1猜测。

## 包级旁证

另在wlan0做90秒限时TCP头观察，仅过滤上述网易云地址/443端口，不转储应用负载；tcpdump退出124表示预定限时结束。该窗口包含14个IPv6 SYN/重传，没有捕获到目标返回的IPv6报文；同时捕获到2个IPv4 SYN-ACK。数据见tcp-headers-redacted.txt，本机源地址已替换别名。该窗口不是全部38次请求的全程抓包，不把包数等同请求数。

## 对之前修复的解释

15秒PING和30秒空闲连接回收仍在，但本轮失败的新连接尚未建立，谈不上依赖PING或池回收解决。独立HTTP/1.1回退若仍按同一系统DNS顺序先连接这个无响应IPv6地址，也可能重复耗尽截止。

此前使用“始终复用坏h2连接”解释当前所有失败的说法缺少依据。本轮给出了另一个已经实际复现的失败链；历史流重置仍应作为独立事件保留，不能改写历史证据。

## 后续工程方向与边界

优先处理目标域的多地址连接回退与预算配合，让首个地址无响应时能在整通截止前尝试其他地址；可评估保留IPv6回退的IPv4优先或有界地址竞速。**2秒只是本轮单变量实验值，没有直接写回全局生产配置**；慢网、多个地址、代理及用户取消都需要配套回归。没有依据全局禁用HTTP/2或IPv6。

本轮没有升级版本、修改业务源码、重打发布包或推送。已有历史曲线测量文件的他人改动保持原样。临时会话/设备身份副本已在每轮结束清理，私有SharedPreferences只在内存解析，不入库。源地址已从socket错误与抓包文本脱敏；服务器目标DNS地址保留便于复核。
