# v2.4.0 探针总结（PROBE-SUMMARY）

> 探针脚本全部在 `docs/verification/v2.4.0/`，原始响应在 `probe-raw/`。
> 全部为**匿名只读**（不发任何写请求、不读任何凭证、不落盘任何隐私字段）。
>
> **匿名态的成因（如实记录）**：本机可用的真机是 WGR-W09（Huawei，Android 12），
> `su` 不存在、`adb root` 被拒（production build）、release 包不可 `run-as`，
> 因此读不到应用内的 QQ / ncm 登录态。
> 匿名态对**目录数据（id / 名称 / 曲目列表 / 专辑列表）没有影响**；
> 对**播放地址**有影响 —— 这一条在下面 C 节里逐项标注。

| 问题 | 结论 | 证据 |
|---|---|---|

| 专辑跨源匹配可行吗 | **可行**，样本 48/48 达到 `≥MEDIUM`（EXACT 40 / HIGH 4 / MEDIUM 4） | `probe-album-mapping.md` |

## 1. 艺人跨源匹配

**可行性：可行。** 但**不能用「同名」判定**。

| 项 | 实测 |
|---|---|
| 共同键 | **没有**。同一艺人 ncm `id=6452`、QQ `singerID=4558`/`singerMID=0025NhlN2yWrP4`，两个编号空间独立 |
| 别名表 | 只有 ncm 有 `alias[]`；QQ 艺人搜索**不返回别名** ⇒ 单边属性，不能做对称判据 |
| 粉丝数 | 两源的艺人搜索都**不返回** |
| 可用的判据 | **艺名（仅用于召回）+ 专辑列表归一化后的重合数** |

**准确率（11 位艺人，含同名歧义与「艺名≠真名」两类）**：

| 置信度 | 本版算法（召回 → 专辑重合 → 分级） | 朴素「同名」算法 |
|---|---|---|
| EXACT | **8** | 2 |
| HIGH | **3** | 8 |
| MEDIUM | 0 | 0 |
| LOW | 0 | 0 |
| NONE | **0** | **1** |

**最重要的一条实测**：`邓紫棋` 这一行，朴素同名算法给 `NONE`（它锚到了 ncm 的**仿冒号**
`邓紫棋`(62017015, 1 张专辑)），而正确答案是 `EXACT`（真身 `G.E.M.邓紫棋` 在两边都在，
ncm 7763 / QQ 001fNHEf1SFEFN，专辑重合 54 张）。
**这就是铁律 17 的实证依据：名字只用来召回，绝不用来判定。**

同名歧义的规模（匿名搜索 top20 内，归一化同名）：
周杰伦在 ncm **3** 个同名字号；`李健` 在 QQ **9** 个同名字号。
真身之间的专辑重合是 9~63 张，仿冒号之间是 0 张 —— **专辑重合度是唯一稳的判据**。

## 2. 专辑跨源匹配

**可行性：可行，且比艺人更稳**（专辑名比艺人名更少歧义，且有曲目名集合可校验）。

| 项 | 实测 |
|---|---|
| 归一化后能配对的专辑 | 48 对（6 位艺人 × top80） |
| 原始字符串**完全相同**的 | 33 / 48 |
| **需要归一化才相等**的 | 15 / 48（`（Deluxe）`、`(Taylor's Version)` 等） |
| 曲目数一致 | 41 / 48（**85%** ⇒ 只能当「EXACT 的加分项」，不能单独当 EXACT 判据） |
| 发行年份一致 | 43 / 48（**90%** ⇒ 可做 MEDIUM 的加分项） |
| 发行方一致 | 8 / 34（⚠️ **不可用**：QQ 的 `company` 常为空、且口径是版权方而非厂牌） |
| **曲目名集合重合率 ≥90%** | 44 / 48（**这是最强的判据**） |

**置信度分布**：EXACT 40 / HIGH 4 / MEDIUM 4 / LOW 0 / NONE 0。

## 3. 单曲跨源匹配

**可行性：可行，但必须分级，且必须有时长判据。**

| 项 | 实测 |
|---|---|
| 数字 id | 两源独立编号（《晴天》ncm `186016` vs QQ `97773`） |
| 字符串 mid | 只有 QQ 有 |
| **`media_mid == mid`** | **0 / 230**（两源实测全部不同）⇒ 取链必须用 `media_mid`，匹配时两个都要留 |
| ISRC / 指纹 | 两源都**不返回** |
| 因此可用的属性 | `曲名 + 艺人 + 专辑 + 时长` |

**时长判据的精度（230 对可比样本）**：

| 时长差 | 数量 |
|---|---|
| ≤1s | 164 |
| 1~2s | 20 |
| 2~10s | 24 |
| 10~30s | 7 |
| **>30s** | **15** |

≤2s 占 **184/230 = 80%**；而 >30s 的 15 条**全部是同名不同版本**
（伴奏 / Live / 加长版）—— 正是时限判据要挡掉的东西。所以**容差取 2s**。

**置信度分布（230 首）**：EXACT 123 (48%) / HIGH 61 (24%) / MEDIUM 46 (18%) / LOW 0 / NONE 26 (10%)。

**同名不同版本的实测样本**（同一张专辑内、归一化曲名相同）：
`Secret (加长快板)` / `Secret (慢板)`；`Enrich Your Life` / `Enrich Your Life(伴奏)`；
`你过得好吗` / `你过得好吗(伴奏)`；`Do You Ever Shine` / `Do You Ever Shine? (BITTER BLOOD Version)`。

## 4. 版权可用性字段

### 4.1 存在性

| 页面 | ncm | qm |
|---|---|---|
| 艺人主页（专辑列表） | ❌ **没有** `privilege` | ❌ 没有（只有专辑元数据） |
| 专辑页（曲目列表） | ❌ **没有** `privilege`；`songs[].st` 实测在本专辑**恒为 `-1`** | ⚠️ 有 `pay.*` / `action.*`，但都是**标签**不是判据 |
| 单曲页 / 批量详情 | ✅ `privileges[].st/pl` + `songs[].noCopyrightRcmd` | ⚠️ 同上 |

**「专辑页 `st` 恒为 -1」是本探针推翻的第一个假设**：
同一张专辑里，周杰伦（ncm**无版权**）与林俊杰（ncm**有版权**）的 `st` **都是 `-1`**，
**零区分度**。这复现并强化了 v2.3.0 规则 5 的「`st == -1` 绝不可当判据」。

### 4.2 没有字段时的降级

| 音源 | 降级手段 | 成本 | 实测 |
|---|---|---|---|
| ncm | 另发 **一次批量** `POST /api/v3/song/detail`（`c=[{id}…]`） | 100 首/请求，~0.3–0.6s | `privileges[].st`：无版权专辑 `-200` / 有版权专辑 `0`，**完全区分** |
| QQ | 另发 **一次批量** `CgiGetVkey`（`songmid[]` + `filename[]`） | 一屏 1 次请求，~0.4–0.8s | 97 首抽样：`purl` 非空 18 / 空 79 |

### 4.3 A/B 对照（标签 vs 金标准）

**ncm（33 首，标签判定与线上 `TrackAvailability.ofNetease` 逐字同构）**：

| 标签判定 | 金标准给**完整**文件 | 只给**试听片段** | 不给文件 |
|---|---|---|---|
| `PLAYABLE` | — | — | — |
| `MEMBER_ONLY` | 0 | **12** | 0 |
| `NO_COPYRIGHT` | 0 | 0 | **21** |
| `UNKNOWN` | 0 | 0 | 0 |

- **假阳性 0**、**假阴性 0**。

**★ 这里有一个第一版探针判错的坑，必须记下来**：`url != null` **不等于**「能完整播放」。
VIP 专享曲在匿名态下**也返回 url**，但 `freeTrialInfo = {start: 0, end: 30}` —— 那是 30 秒试听
（《倔强》`end=30`；Taylor Swift 那批 `end=45`）。
第一版只判 `url != null`，把 12 首「会员专享 + 试听」误判成假阴性，
差点得出「v2.3.0 的判据过保守、应该放宽」的错误结论。
**正确的金标准是 `url != null && freeTrialInfo == null`。**

**QQ（97 首）**：

| 判据 | 取值分布 | 能不能用 |
|---|---|---|
| `action.switch` bit0 | **bit0=1 × 97（100%）** | ❌ 零区分度（复现 v2.3.0 的 130/130） |
| `action.alert` | 2×42, 11×4, 21×12, 22×24, 41×15 | ❌ 语义无权威定义 |
| `pay.pay_play` | `(0, 有purl)×18`、`(1, 无purl)×79` | ⚠️ 只能标「VIP」，**不能标「无版权」** |
| **`CgiGetVkey` 的 `purl` 非空** | 有 18 / 无 79 | ✅ **唯一诚实的「这个源现在能不能播」判据** |

> QQ 匿名可播率另测（12 关键词 × 30 首 = 360 首）：**52/360 = 14.4%**，
> 说明 `purl` 判据**有阳性样本**，不是恒假。

### 4.4 本版写进代码的判据

| 音源 | 可播放 | 需会员 | 无版权 | 其余 |
|---|---|---|---|---|
| ncm | `pl > 0` | `st == 0 && pl == 0 && fee ∈ {1,4}` | `st == -200` 或 `noCopyrightRcmd != null` | `UNKNOWN` |
| QQ | **vkey 预检 `purl` 非空** | `purl` 空且 `result == 104003`，或 `pay_play == 1` | **不判** | `UNKNOWN` |

排序：**`PLAYABLE` > `UNKNOWN` > `MEMBER_ONLY` > `NO_COPYRIGHT`**。
`UNKNOWN` 排在受限项之前，因为「不知道」不等于「不能播」，把它沉底等于凭空说它不能播。

## 5. 匹配失败时的降级策略（四个页面统一）

1. **`confidence < MEDIUM` 一律不合并**（铁律 17）：两侧各自成行、各自标音源。
2. **不用 `LOW` 去选默认音源**：默认音源由**可播放性**决定，不由匹配结果决定。
3. **失败不缓存**：`NONE` / `LOW` 不写匹配缓存，下次进页面重试（缓存只存 `≥MEDIUM`）。
4. **人工入口常在**：三个页面都有「只看 ncm / 只看 QQ / 双源聚合」切换。
5. **不隐式归一繁简与别名**：`周杰伦` 与 `周杰倫` 在本版**视为两个艺人**。
6. **版权判不出来就留白**：`UNKNOWN` 不显示任何角标，不写「可能无版权」当结论
   （只在**有失败记录**时才写「可能」，见实现）。

## 6. 两源接口能力差异（做聚合必须知道的）

| 能力 | ncm | qm |
|---|---|---|
| 艺人 → 专辑列表 | `GET /api/artist/albums/{id}` ✅ 带 `size`（曲目数） | `fcg_v8_singer_album.fcg` ✅ 带 `latest_song.song_count` |
| 同上（另一个端点） | — | `musicu` `GetAlbumList` ⚠️ **`totalNum` 恒为 0** |
| 艺人 → 热门曲 | `GET /api/v1/artist/{id}` ✅ | `get_singer_detail_info` ✅ |
| 艺人详情 | `GET /api/artist/detail/{id}` ❌ **404** | 无独立端点 |
| 专辑 → 曲目 | `GET /api/v1/album/{id}` ✅ 一次全量 | `GetAlbumSongList` ✅ 支持 offset |
| 专辑元数据专端点 | 不存在（详情里带） | `GetAlbumInfo` ❌ **`code=40000`** |
| 单曲详情 | `POST /api/v3/song/detail` ✅ **批量 ≤100** | `get_song_detail_yqq` 单首 |
| 播放地址 | 单首 | `CgiGetVkey` ✅ **批量** |
| 歌词 | `POST /api/song/lyric` | `GetPlayLyricInfo` |
| 列表级版权字段 | ❌ 必须补批量详情 | ❌ 必须补批量预检 |
| 曲目数字 id 命名空间 | 十进制 | 十进制，**但与 ncm 独立**；本应用用 bit62 标志位隔离 |
| 时间字段单位 | `publishTime` / `dt` = **毫秒** | `pubTime` = `YYYY-MM-DD` 字符串、`interval` = **秒** |

## 7. 由探针直接决定的设计取舍（逐条可追溯）

| 取舍 | 依据 |
|---|---|
| 艺人匹配必须「召回 → 专辑重合 → 分级」三步 | P6：朴素同名在邓紫棋上给 NONE，正确是 EXACT |
| 专辑 `EXACT` 要求「曲目数一致 **且** 曲目名重合率 ≥90%」 | 曲目数只一致 41/48，单独用会把 7 对错判 |
| 单曲 `EXACT` 要求「曲名 + 艺人 + 时长 ≤2s + 版本标记一致」 | >30s 的 15 条全是同名不同版本 |
| 版权排序用 4 档 `rankGroup` 而不是二分 | `UNKNOWN` 不能当「不能播」 |
| QQ 不标「无版权」 | 没有任何字段能证明「没上架」 |
| 播放预检必须并行且失败不阻塞 | C2 成本 + 铁律 5 |
| 匹配缓存只存 `≥MEDIUM` | 铁律 17 + 失败可重试 |

## 8. 未验证项（如实）

1. **登录态下的判据**：本探针全程匿名。VIP 账号下 QQ `purl` 的覆盖率、ncm `pl` 的取值
   都需要登录态再测一次。**代码里已经按「用应用自己的身份发预检」实现**，
   所以真机上登录后的结果会与本文档的匿名数字不同（方向是「更多 `PLAYABLE`」）。
2. **QQ 单曲详情是否有批量端点**：本轮只验证了 `get_song_detail_yqq` 单首形状，
   没有穷举 `musicu` 的其他 module/method 组合。
3. **繁简/别名归一化**：本轮只证明「不做是安全的」，没有评估「做了会错多少」。
4. **匹配算法在极端同名场景（如「李健」9 个同名字号）下的完整准确率**：
   本轮只验证了 top20 召回 + 专辑数排序能锚到真身，没有做全量人工标注。
5. **QQ `action.alert` 的语义**：取值分布已记录（2/11/21/22/41），但无权威定义可验证。
