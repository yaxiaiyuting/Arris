# 探针 ③：**官方版本标签**的数据来源与定义

> v2.3.0 · 2026-09-26 匿名实测。原始数据：`probe-raw/probe-copyright-semantics.txt`、
> `probe-raw/probe-judgement-validity.txt`、`probe-raw/probe-qq-fields.txt`。
> 复现脚本：`probe-copyright-semantics.py`、`probe-judgement-validity.py`、`probe-qq-fields.py`。

## 0. 先拍板：什么算「官方版本」

任务书要求先定义再实现。本版的定义**刻意收窄到能被服务端字段确证的那一种**：

| 概念 | 本版是否实现 | 判据 | 为什么 |
|---|---|---|---|
| **原唱**（这一条就是原曲本身） | ✅ 实现 | ncm `originCoverType == 1` | 服务端显式声明 + 自洽率 96.7% |
| **翻唱**（这一条是别人的翻唱/改编） | ✅ 实现（并显示原曲名/原唱者） | ncm `originCoverType == 2`（51% 另带 `originSongSimpleData`） | 同上 |
| 官方音源 vs 用户上传 | ❌ **不实现** | 无字段 | 见 §3：没有可确证判据 |
| 官方发行 vs 用户自制 | ❌ 不实现 | 无字段 | 同上 |
| qm 的任何官方/原唱标签 | ❌ **不实现** | 无字段 | 见 §4：QQ 一个相关字段都没有 |

**「原唱 / 翻唱」这一对是唯一的例外** —— 不是启发式，是**接口字段**。下一节给证据。

---

## 1. ncm：`originCoverType` 是接口字段，不是猜的

### 1.1 字段存在性与取值分布

字段普查（`probe-copyright-semantics.txt`）在单曲级发现：

```
originCoverType            ← 整数枚举
originSongSimpleData {     ← 只在 originCoverType == 2 时出现
    songId, name,
    artists[{id,name}],
    albumMeta{id,name}
}
```

591 条去重样本的分布（`probe-judgement-validity.txt`）：

```
originCoverType 分布 = {"1": 429, "2": 198, "0": 79, "3": 22}
```

| 取值 | 条数 | 本版解释 |
|---|---|---|
| `1` | 429 | **原唱** |
| `2` | 198 | **翻唱**（其中 101 条，51%，带 `originSongSimpleData`） |
| `0` | 79 | 无信息（实测多为 UP 主自制 beat / 采样 / 纯音乐） → **不打标签** |
| `3` | 22 | 语义未确证（实测混有 DJ 版 / R&B 版与普通条目） → **不打标签** |

### 1.2 自洽性检验（不靠我当裁判）

做法：对每条 `originCoverType == 2` 且带 `originSongSimpleData.songId` 的记录，
**回头去查它自己声称的那首「原曲」**，看那首的 `originCoverType` 是不是 `1`。
这检验的是「服务端自己的 1/2 语义是否自洽」，不需要我先认定谁是原唱。

实测（`random.seed(20260926)`，抽查 60 条，`probe-judgement-validity.txt`）：

```
原曲 oct==1（自洽）= 58；原曲 oct!=1（不自洽）= 2；查不到 = 0
原曲 oct 分布 = {"1": 58, "0": 2}
自洽率 = 58/60 = 96.7%
```

两条「不自洽」的原曲取值都是 `0`（**无信息**），不是 `2` 或 `3`（错误的另一侧）——
也就是说这 2 条是「服务端对原曲也没打标」，而不是「服务端指错了原曲」。
**没有任何一条出现「翻唱指向另一条翻唱」**。

### 1.3 反向对照：`1` 从不带 `originSongSimpleData`

```
oct==1（假设=原唱） 共 429 条，其中带 originSongSimpleData 的 0 条
oct==2（假设=翻唱） 共 198 条，其中带 originSongSimpleData.songId 的 101 条 (51%)
```

`originSongSimpleData` 的字段名就是「**原曲**的简版信息」。它**只在 `2` 上出现、在 `1` 上从不出现**
—— 这是对「1=原唱 / 2=翻唱」最直接的旁证。

抽样明细（节选，完整 60 条见 `probe-judgement-validity.txt`）：

```
翻唱《晴天 (女声版))》    → 原曲《晴天》/ 周杰伦          oct=1  id=186016
翻唱《起风了(林俊杰)》     → 原曲《起风了》/ 冯沁苑(买辣椒也用券) oct=1  id=1330348068
翻唱《千本桜》          → 原曲《千本桜》/ 黒うさP,初音ミク     oct=1  id=26096272
翻唱《孤勇者(35秒)》      → 原曲《孤勇者》/ 陈奕迅           oct=1  id=1901371647
翻唱《稻香 (钢琴版)(原唱：周杰伦)》 → 原曲《稻香》/ 周杰伦      oct=1  id=185709
```

**准确率结论：96.7%（58/60），且剩余 3.3% 全部落在「不知道」而不是「说反了」。**

### 1.4 为什么这不是「不可靠的启发式」

任务书禁止的是**启发式**（用曲名/艺人名字符串去猜）。本版用的是：

- 服务端下发的**枚举字段** `originCoverType`；
- 服务端下发的**结构化原曲引用** `originSongSimpleData.songId`（可精确回查，不是字符串匹配）。

这两者都不是「我们猜的」。所以本版只在这两个字段上打标签，
**绝不**用「曲名里带『翻唱』两个字」「艺人名与专辑艺人不同」这类启发式。

> 反例正好在样本里：`晴天 (原唱 周杰伦)` 这种**标题里自称「原唱」**的条目，
> `originCoverType = 2` —— **它是翻唱**。靠字符串关键字判断会 100% 判反。
> 这就是「不许用启发式」的实证理由。

## 2. 展示口径

| 标签 | 触发 | 展示 | 位置 |
|---|---|---|---|
| **原唱** | `originCoverType == 1` | 小角标「原唱」 | 歌名**后**，与音源角标同一行 |
| **翻唱** | `originCoverType == 2` | 小角标「翻唱」；若 `originSongSimpleData` 有值，副标题补 `原唱：<艺人> · <曲名>` | 同上 |
| 无标签 | `0` / `3` / 字段缺失 | **什么都不显示** | — |

样式约束（任务书 6.3）：小角标、不抢主视觉、只在明确可判时显示。
截图见 `screenshots/` 与 `verification/`。

## 3. 明确**不做**的：「官方音源 vs 用户上传」

探测过的候选判据与它们为什么不能用：

| 候选 | 实测结果 | 为什么不能用 |
|---|---|---|
| `copyright` | 取值 `{0,1,2}`，与「是不是用户上传」不相关（实测 `晴天` 官方版 `copyright` 缺失、`晴天(深情版)` 也是） | 语义未知，无金标准 |
| `resourceState` | 全部样本恒为 `true` | 无区分度 |
| `ftype` / `rtype` | 全部样本恒为 `0` | 无区分度 |
| `single` | 字段存在，但与「官方发行」无对应关系 | 语义未知 |
| `version` | 是**修订号**（取值 1~632 无规律） | 与「版本」语义无关（v1.5.0 已证明 `yrc.version` 同理） |
| `privilege.chargeInfoList[].chargeType` | 只是各码率的收费方式 | 与上传来源无关 |
| 专辑名 / 艺人名模糊匹配 | — | **启发式，禁止** |

⇒ **不实现**。QQ 侧同理（§4）。

## 4. qm：**一个相关字段都没有**

字段普查（6 组关键词 × 130 条，`probe-raw/probe-qq-fields.txt`）
筛出的疑似字段只有：

```
疑似相关字段：['label', 'singer[].type', 'tag', 'type', 'version']
```

逐个排除：

| 字段 | 实测取值 | 结论 |
|---|---|---|
| `label` | **130/130 全是 `0`** | 无区分度（QQ 的「独家/首发」标记，本轮样本里一个都没出现） |
| `type` | **130/130 全是 `0`** | 无区分度 |
| `songtype` | **字段不存在**（`new_json=1` 下没有这个 key） | 不可用 |
| `ov` | **130/130 全是 `0`** | 无区分度 |
| `version` | 仅部分条目有 | 是版本号/修订号，非「原唱/翻唱」 |
| `singer[].type` | 全部为 `0` | 无区分度 |
| `tag` | 存在但样本内无取值差异 | 语义未知 |
| `album.id` / `time_public` | 全部有值 | **官方与翻唱都有**（见下） |

反例证据 —— **QQ 搜索结果里的翻唱与官方版字段完全一样**：

```
晴天         mid=002DMfDx1macLz  alb=叶惠美            singer=周杰伦   label=0 type=0 ov=0   ← 官方
晴天         mid=001lkR2X1ZQg8b  alb=晴天 (深情版)       singer=Lucky小爱 label=0 type=0 ov=0   ← 翻唱
晴天         mid=003TtLEa1F5EHc  alb=晴天 (独唱版)       singer=梅菜扣肉肉 label=0 type=0 ov=0   ← 翻唱
晴天         mid=004MA5TJ0Gwa5n  alb=再次寻找周杰伦        singer=刘瑞琦   label=0 type=0 ov=0   ← 翻唱
```

四条的 `label` / `type` / `ov` / `singer[].type` **逐字段相同**。

⇒ **QQ 侧不实现任何官方/原唱标签。**（任务书 6.2 明确允许：「准确率不足时，只做明确可判的标签」
/「是否接受不实现」。这是**接受不实现**的那一支。）

### 4.1 为什么不用「艺人名匹配」启发式

一个看起来可行的启发式是「`singer[].name` 与专辑艺人一致 ⇒ 官方」。
上面的反例直接证伪：`晴天/梅菜扣肉肉` 的专辑就是**她自己的**《晴天 (独唱版)》——
艺人名与专辑艺人一致，但它是翻唱。同理 `刘瑞琦` 的专辑《再次寻找周杰伦》也是她自己的。

⇒ 该启发式会把**翻唱标成官方**，正是任务书禁止的「给用户错误标签」。

---

## 5. 本版的实现边界（一句话）

> **只在 ncm、且只在 `originCoverType ∈ {1, 2}` 时显示「原唱 / 翻唱」角标；
> 其余全部留白。QQ 不显示任何官方/原唱标签。**

## 6. 未验证 / 边界（如实）

1. `originCoverType == 3` 的语义未确证（22 条样本混有 DJ 版与普通条目）——
   本版**不打标签**，这是保守的一侧。
2. 「原唱」是**ncm 自己的声明**，不是版权法意义上的权威认定。
   本版文案用「原唱」，语义是「ncm 标注的原曲」；不写「官方」「正版」这类更强的措辞。
3. 96.7% 的自洽率是在 60 条抽查上得到的，样本量有限；剩余 3.3% 落在「不知道」一侧，
   所以最坏情况是**少标**，不是**标错**。
4. 翻唱标签里的「原唱：X · Y」只在 `originSongSimpleData` 存在时显示（198 条里 101 条，51%）；
   其余翻唱只显示「翻唱」两个字，不猜原曲是谁。
