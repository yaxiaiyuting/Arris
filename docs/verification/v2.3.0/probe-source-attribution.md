# 探针 ②：搜索结果里的**音源归属**

> v2.3.0 · 代码审计 + 2026-09-26 匿名实测。原始响应在 `probe-raw/qq-search-*.json`
> 与 `probe-raw/ne-search-*.json`。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 同一首歌两个源都有时，接口能不能告诉我「这是同一首」？ | **不能**。两个平台各自编号，没有任何跨源标识（无 ISRC / 无音乐指纹字段） |
| 现在界面怎么标？ | **只标 QQ，不标 ncm**（`SongCard` 的 `sourceBadge` 对 ncm 返回空串）—— 这是「看不出结果来自哪里」的根因 |
| 有没有跨源去重？ | **没有**，而且**是有意的**（`SearchViewModel.publish` 用 `distinctBy { it.trackKey }`，两源的 key 天然不同）⇒ 同一首歌会出现两行 |
| 那「两源都有」怎么让用户看出来？ | 只能**按行标音源**，不能靠合并成一个条目。本版把「ncm」也标出来，并把两源候选都摆在同一列表里 |
| QQ 有没有「能不能播」的字段？ | **没有可用的**。`action.switch` 的 bit0 在 **130/130 条上恒为 1**（不区分）；`action.alert` 语义无权威定义，**不用** |

---

## 1. 身份：两套编号，没有跨源标识

`TrackKey` 的相等性是 `(source, id)`（v2.1.5 固化），这**不是偷懒，是接口事实**：

- ncm `songs[i].id`：十进制百万~十亿量级；
- qm `songs[i].id`（`new_json=1` 下）：另一套独立编号，另有 `mid`（形如 `0039MnYb0qxYhV`）
  与 `file.media_mid`（**经常与 `mid` 不同**，v2.1.0 的实测结论）。

实测两源同关键词「晴天」的返回（`probe-qq-fields.txt` §Q1 与 `probe-copyright-semantics.txt`）：

| 源 | 曲名 | 平台 id | 归属艺人 | 专辑 |
|---|---|---|---|---|
| ncm | 晴天 | `186016` | 周杰伦 | 叶惠美 |
| qm | 晴天 | `mid=00083kc41YcFuR`，`media_mid=00083kc41YcFuR` | 周杰伦 | 哄你入睡的流行钢琴曲（**另一条**） |
| qm | 晴天 | `mid=002DMfDx1macLz` | 周杰伦 | 叶惠美 |

两边**都没有** ISRC、MusicBrainz ID、音频指纹之类的跨平台标识字段
（字段普查见 `probe-raw/probe-qq-fields.txt` 的「全部字段」一节：
QQ 侧单曲级字段里没有 `isrc`；ncm 侧同样没有）。

⇒ **跨源合并不可做**（也是任务书明确排除的）。「两源都有」只能表达为**两行 + 清晰的音源标签**。

## 2. 现状：只有 QQ 被标出来

```kotlin
// ui/components/SongCard.kt:61-64（v2.1.0 · E 的原文）
val sourceBadge = when (song.musicSource) {
    MusicSource.QQMUSIC -> strings.sourceQqMusic
    else -> ""                       // ← ncm不标
}
```

设计理由（当时的注释）是「ncm 是本应用原本的唯一音源，给每一行都挂标签只会变成噪音」。
这个理由在**只有 ncm**的时代成立；到了 v2.3.0，聚合搜索会把两源的条目**混在同一个列表**里，
而两源的 `id` 完全不同、曲名可能完全一样（上面的「晴天」就是三行同名）——
**不给 ncm 标注 = 用户无法判断哪一行是哪个源**。

同时 `SearchScreen` 顶部只有一行汇总小字（`strings.sourceSummary(ncm数, QQ 数)`），
它回答的是「这一页各有多少条」，**不回答「这一行是谁的」**。

> 真机反馈原话（v2.1.0 记录）：「现在有了稻香，似乎是 ncm 的搜索结果？」——
> 说明这个歧义在 v2.1.0 就已经被用户提出来了，只是当时的解法（顶部一行汇总）不够。

## 3. qm 一侧的「可播放 / 无版权」字段：**没有**

对 6 组关键词、130 条 QQ 搜索结果做字段普查（`probe-raw/probe-qq-fields.txt`）：

```
pay.pay_play 分布: {"1": 36, "0": 4}          ← 已在 v2.1.4 用于「会员专享」
action.switch 取值: {16881409: 72, 81719: 17, 16889603: 15, 1: 2, 77623: 4, 81683: 23, ...}
action.alert  取值: {41: 57, 11: 48, 2: 61, 42: 10, 50: 2, 53: 2}
```

`action.switch` 的 **bit0 在全部 130 条上都是 1**（`probe-qq-fields.txt` 的位表），
没有任何区分度；其余位的组合与 `pay_play` / `alert` 的关系**不稳定**
（例如 `alert=2` 同时出现在 `switch=16881409, pay_play=1` 与 `switch=16889603, pay_play=0` 上）。

`action.alert` 的取值语义**没有权威定义**（QQ 官方未公开，社区文档互相矛盾），
且本次探针**没有**可用于验证它的金标准（QQ 的取链要带签名的 `comm` 信封，
本轮的匿名探针通道跑不通）—— 按项目纪律「拿不到实测参数时不许拿标签当证据」
（AGENTS.md v2.2.1 规则 3），**不使用** `action.alert`。

⇒ **QQ 侧本版不做任何「可播放 / 无版权」断言**，只保留 v2.1.4 已验证的
`pay.pay_play == 1 ⇒ 会员专享`，并在播放失败时走**降级提示**（见 `probe-copyright.md` §4）。

## 4. ncm vs QQ 的字段能力对照（本版的输入）

| 能力 | ncm | qm |
|---|---|---|
| 逐曲 `privilege` | ✅ `songs[i].privilege`（240/240） | ❌ 无 |
| 「可播放」零假阳性判据 | ✅ `pl > 0`（30/30） | ❌ 无 |
| 「需会员」判据 | ✅ `st==0 && pl==0 && fee∈{1,4}` | ✅ `pay.pay_play == 1` |
| 「无版权」显式声明 | ✅ `st == -200` / `noCopyrightRcmd` | ❌ 无 |
| 「原唱 / 翻唱」 | ✅ `originCoverType`（见 `probe-official-tag.md`） | ❌ 无 |
| 艺人页 / 专辑页 | ✅ `hotSongs[i].privilege` / 顶层 `privileges[]` | ✅ 同一套（QQ 歌单详情已带 `pay`） |
| 跨源同一性 | ❌ | ❌ |

**这张表就是「按探针结论实现」的落点**：ncm 能确证就确证，QQ 确证不了就沉默 + 降级提示。

## 5. 本版的实现方向（探针结论 → 设计）

1. **每一行都标音源**：`SongCard` 的音源角标从「只标 QQ」改成
   「**两源都标**，但 ncm 用弱化样式」——既消歧义，又不制造噪音（见实现说明）。
2. **同一首歌两源都有 ⇒ 两行，各有各的源标**：不合并、不隐藏（任务书第 5.1 条）。
3. **版权标注按能力表分源实施**：ncm 标「可播放 / 需会员 / 无版权」，
   QQ 只标「会员」（`pay_play`），其余留白。
4. **排序**（任务书第 5.3 条）：在 v2.1.4 的 `SearchRanking` 之上**只加一条**——
   同档内「可播放」优先于「未知」。「未知」与「受限」保持同组靠后，
   **绝不把「不知道」当成「能播」**（`TrackAccess.UNKNOWN` 的既有约定）。

## 6. 未验证 / 边界（如实）

1. 「同一首歌两源都有」用的是**曲名 + 艺人**的人工比对，不是程序判定；
   程序上两源就是两条独立记录，本版**不做**自动配对。
2. QQ 的 `action.alert` / `action.switch` 高位含义未探明；本轮只证明
   「bit0 无区分度」，**不证明**其它位没有含义。要否定一个字段需要能验证它的金标准，
   而 QQ 的取链金标准本轮没打通 —— 这条如实记为缺口。
3. QQ 未登录时能否搜到（`QqAccountAvailability.allowAnonymousSearch`）是另一个既有开关，
   本轮未改。
