# v2.6.1-gpl

**versionCode 49** · `minSdk 24`（Android 7.0 / 3 GB RAM 可用）· GPLv3（原代码 MIT）· 无新增权限

> **P0 hotfix。** 只修一个用户可见缺陷 + 补它的回归面，不引入新功能。
> qm 曲目的「转到歌手」以前会把用户送到**另一个歌手**的页面
> （《稻香》→ 马洪波）。现在它进的是**正确的 QQ 艺人页**；
> 拿不到可信身份时改为**跳搜索并给出提示**，而不是猜一个人出来，也不是毫无反应。

## 1. 探针结论（先探针，后改代码）

> 完整数据：`docs/verification/v2.6.1/PROBE-SUMMARY.md`
> 证据索引：`docs/verification/v2.6.1/EVIDENCE.md`
> 接口取证脚本可重跑：`docs/verification/v2.6.1/probe-raw/probe-artist-id-collision.sh`

### 1.1 复现路径与稳定性

| 设备 | 路径 | 修复前 | 稳定性 |
|---|---|---|---|
| WGR-W09（华为平板 / Android 12） | 搜索 `Jay Chou` → 长按 QQ《晴天》→ 转到歌手 | **马洪波**（专辑 5 / 单曲 40） | 5/5 |
| PCL110（OPPO 手机 / Android 16） | 同上 | **马洪波** | 2/2 |
| PCL110 | 冷启动后 → 播放器点歌名 → 转到歌手 | **毫无反应** | 2/2 |

### 1.2 马洪波是谁，他从哪来

**ncm 的艺人 `4558`**（实测 `GET /api/artist/4558` → `code 200, name="马洪波"`）。
而 `4558` 恰好是 **QQ 的周杰伦**的数字 `singerID`：

| QQ 歌手 | QQ `singer.id` | QQ `singer.mid` | 当成 ncm id 查出来 |
|---|---|---|---|
| 周杰伦 | `4558` | `0025NhlN2yWrP4` | **马洪波**（专辑 1 / 单曲 32，**页面看起来完全正常**） |
| 林俊杰 | `4286` | `001BLpXF2DyJe2` | 刘子译（0 / 0，空页面） |
| 陈奕迅 | `143` | `003Nz2So3XXYek` | 404（报错） |

他不是某个 fallback 值（不是 0 / -1 / null 转换来的），也不是"API 失败时返回的第一条"
—— 那条请求 **code 200、成功命中了一个真实艺人**。这正是最坏的一档：
页面有头像、有专辑、有单曲，用户会以为**这个应用的艺人数据整体是错的**。

### 1.3 根因：两个独立的身份缺陷，叠在同一条路径上

| # | 位置（v2.6.0） | 做了什么 |
|---|---|---|
| 1 | `qq/QqSongMapper.kt:110` | 只取 `singer[].id`，**丢掉同一个对象上一直存在的 `singer[].mid`**；`ArtistItem` 当时也没有字段装它 |
| 2 | `MainActivity.resolveAndNavigate` | 只读 `artists[0].id` 就跳，**从不读 `song.musicSource`** |
| 3 | `NavGraph.kt` 的老路由 `artist/{artistId}` | composable 里 `sourceKey = MusicSource.NETEASE.key` **写死** |

外加一条只影响"没反应"的：

| 4 | 同 #2 的补 id 回落 | 打的是**ncm** `song/detail`；QQ 曲目的 id 带 bit62 标志位，在那里必然查空 ⇒ `when` 一个分支都不匹配 ⇒ **静默放弃** |

> 顺带纠正一条**写进代码注释的错误结论**：`AlbumDetailScreen.kt:170-172` 说
> 「QQ 一侧拿不到 `singerMID`」。实测 QQ `singer[]` 的字段集是
> `{id, mid, name, pmid, title, title_highlight, type, uin}` —— **`mid` 一直在**。
> 那句话对**专辑接口**成立，对**搜索接口**不成立。

### 1.4 任务书的三条前提被推翻（如实记录）

| 任务书假设 | 实测 |
|---|---|
| 走了 v2.4.0 跨源匹配、置信度不足 | **完全没走匹配** —— 这条路径上一次都没调用 `CrossSourceMatcher` / `MatchCacheStore` / `MatchConfidence` |
| 存在 fallback 跳默认艺人 | **不存在**。存在的是"补一次**ncm** `song/detail`"，见上表 #4 |
| 匹配缓存被污染 | **没污染**，而且它存的恰恰是**正确**答案：`artist:netease:6452 → {qqmusic, 0025NhlN2yWrP4, 周杰伦, EXACT, 专辑重合 33 张}` |

### 1.5 影响范围

- **只有 QQ**：ncm 曲目的 `artists[0].id` 就是 ncm 艺人 id，老路由写死的源恰好正确（已做回归）。
- **不止二级菜单**：**播放页竖屏托盘的作者名**是第二个独立入口、同一个错法。
- **不止周杰伦**：见 §1.2 的表 —— 只是周杰伦那一档"看起来最像真的"。
- 二级菜单本身挂在 9 个宿主页面上（首页/搜索/收藏/歌单/QQ 歌单/本地歌单/专辑/艺人/播放器）。

### 1.6 用户报告的「手机没反应 / 平板跳错」不是平台差异

同机交叉 A/B（同一台 PCL110、同一账号、同一页面、同一组坐标，**只改当前歌曲的来源**）：

| 当前歌曲来源 | `artists[0]` | 结果 |
|---|---|---|
| force-stop 后冷启动恢复（`PlaybackStateManager`） | 只有 `name`，`id == null` | **没反应** |
| 搜索结果里点一下那一行 | `id = 4558`（QQ 数字域） | **跳到马洪波** |

两轮之间只差一次点击。**分界是数据形状，不是机型。**
（若不先做这一步 A/B，修复方向会跑去找 ColorOS / HarmonyOS 的差异。）

## 2. 修复说明

### 2.1 身份必须带音源

- **`ArtistItem` 新增 `mid: String?`**（可空 + 默认值，Gson/Unsafe 安全），
  在 `QqSongMapper` 与 `QqCatalogMapper` 两条映射链路上一起填，加对称单测钉住逐值一致。
- **新增 `source/ArtistNavigator.kt`**：「转到歌手」的**唯一**身份判定（纯逻辑、无 Android 依赖）。
  产出三态 —— `进本源艺人页` / `跳搜索` / `什么都不做`。
  **类型上不存在"跳到另一个源"**：把它排除在类型之外，比在实现里小心不提更可靠。
- **值域闸门** `idDomainMatches(source, id)`：ncm 吃十进制、QQ 吃 base62 的 `singerMID`，
  **纯数字的 QQ `singerID` 在 QQ 域不是合法身份**，在闸门上就被拦下。
- **置信度闸门** `crossSourceJump(confidence, targetSource, targetId)`：任何跨源候选都必须
  拿到 `MatchConfidence.mergeable`（>= MEDIUM，全应用唯一阈值）**且**目标值域合法，
  否则跳搜索。阈值不许在调用方写。

### 2.2 拿不到身份就跳搜索，并且说出来

身份不可信时切到搜索 tab、预填艺人名，并给一句提示
（`SourceStrings.artistNavSearchFallback` =「未找到该歌手的准确身份，已为你搜索」）
+ 一条 `TAG_ARTIST_NAV` 日志。

修复前这条路径在 release 包上**零日志**（无菜单日志、无路由日志、无 HTTP 日志 ——
`HttpLoggingInterceptor` 是 `BuildConfig.DEBUG`-only），这也是它拖到用户报告才发现的原因之一。

### 2.3 两个入口收敛到同一个出口

长按菜单的「转到歌手」与**播放页托盘的作者名**以前是两套判据（后者甚至只收一个裸
`Long`、还用 `id != null` 当"能不能进艺人页"的判据 —— 而冷启动恢复的曲目恰好恒为 null）。
现在两个入口都走 `navigateToArtist`。

### 2.4 顺带修掉的三处

| 问题 | 处置 |
|---|---|
| 路由不带艺人名 ⇒ QQ 艺人页标题显示「未知艺人」，且对端召回**静默**为空 | 路由新增 `artistName` 段（URL 编码）；`ArtistNav.Direct` 带 `name`，语义写死为**只作展示与召回**，绝不参与身份判定 |
| `PlaylistCacheCodec` 的扁平 DTO 会丢 `mid`（QQ 歌单入口会静默降级为跳搜索） | DTO 补字段 + 往返单测 + 老条目读成 `null` 的单测 |
| 剪贴板链接 / 音乐人推荐卡 / 搜索艺人 tab 三个"按构造就是 ncm"的入口没有**写出**音源 | 显式写 `MusicSource.NETEASE`；「按构造正确」正是本 P0 里唯一没被写下来的东西。守卫是**源码扫描**单测 |

## 4. 未验证缺口清单（如实列出）

1. **搜索页「艺人」tab → 艺人页**：该 tab 至今只由 ncm 的 `cloudsearch/pc type=100`
   填充（探针已证）。本版把它改成**显式**带 `MusicSource.NETEASE`，
   行为与修复前逐字节相同，但**没有单独做真机点击**；守卫是源码扫描单测。
2. **「单曲信息」页 → 艺人**：该页**没有**艺人入口（艺人是纯文本），所以不存在可验路径。
3. **QQ 歌单详情 / 本地歌单 / 收藏页 长按 → 转到歌手**：与已验证的「搜索结果长按」
   走**同一个** `SongMenuSheet` → 同一个 `navigateToArtist`（代码路径唯一），
   但**没有逐个页面点过**。
4. **S6（Android 7.0 / SM-G9209）未复测**：该机上长按歌曲行会被播放器拖拽层吃掉，
   取不到二级菜单。本版结论由 PCL110（Android 16）+ WGR-W09（Android 12）两台构成。
5. **`PlaylistCacheCodec` 老缓存的自愈时序**：单测覆盖「缺 mid 读成 null」，
   但「下一次联网刷新写回 mid」只有单测证据，没有真机时序证据。
6. **QQ 艺人页的内容未逐字段与官方 App 对比**：本版验证到「进的是 QQ 源的
   `singerMID`、标题是周杰伦、专辑行都是周杰伦且标 qm」为止。
7. **「转到专辑」对 QQ 曲目仍然错**（同类 bug，**本版明确不修**）：
   需要 QQ 的 `albumMID` 而 `AlbumItem` 不带；为它再加一次跨表迁移 +
   5 张持久化结构的回归，会把一次 hotfix 的面扩大到半个数据层。

**本版不声称**任何性能结论（没有逐帧路径改动，也没有跑基准，见铁律 22）。
**本版未触碰**华为控制中心卡片相关代码。

## 5. 新增的三条铁律

写进 `AGENTS.md`（26 / 27 / 28）：

26. **跨源身份跳转必须携带 source，不得只传数值 ID。**
27. **匹配置信度不足时宁可跳搜索，不可跳错误艺人。**
28. **跳转错误比找不到更严重 —— 找不到用户能理解，跳错会让用户以为数据错乱。**

第 28 条不是修辞，它是本次三档失败的实测排序：只有"跳到真人"那一档会让用户
对整个数据层失去信任。

## 6. 用户在界面上会看到什么

1. **QQ 曲目的「转到歌手」进的是 QQ 源的这位歌手**，不再跳到不相干的人。
   （QQ 艺人页以前**根本不可达**，本版第一次打开它。）
2. 少数情况下（老数据、服务端没给 `singerMID`）会**跳到搜索结果**并提示
   「未找到该歌手的准确身份，已为你搜索」—— 不再毫无反应。
3. ncm 曲目的行为**逐字节不变**。
