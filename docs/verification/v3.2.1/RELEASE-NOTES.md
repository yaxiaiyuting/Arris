## v3.2.1-gpl（versionCode 56）

这一版**没有新功能**，只做三个 P0 修复与一套代码体积监控。

### 1. 修掉「放着歌突然闪退」（P0）

播放器卡片原来是一个**单个方法就有 9092 条指令**的巨无霸（编译它一个方法要分配 45MB 内存）——
这是从 v2.0.0 一路带下来的结构性问题。本版按「三个布局分支 + 托盘 + 封面 + 背景 + 状态」
拆成 **15 个部分**，最大的一块只剩 **1972 条指令**（−78%）。

真机验收：**S6 上 10 次冷启动全部无崩溃**（历史复现率约 5 次崩 2 次）。

### 2. 修掉「宽度算出 0 就直接崩」的隐患（P0）

播放器左右两栏的宽度按比例算：右栏有「最小宽度」保险、**左栏没有** —— 一旦算出 0，
不是"宽度变 0"而是**整个 App 崩掉**。本版两侧都装上保险，并且挡住了一个更隐蔽的情况
（算出 `NaN` 时原来的写法**也挡不住**）。

### 3. 修掉「B站登录一打开就显示『二维码已失效』」（P0）

原因有两层：① 界面把「申请二维码」和「等扫码结果」写成了**一步**，二维码要等轮询
（最长 180 秒）结束才被画出来；② 二维码区在"还没有图"时一律显示「已失效」。

现在：**申请 → 先画出二维码 → 再轮询**；二维码区文案分三档
（**加载中 / 已失效请刷新 / 获取失败**），生成失败给明确错误而不是"已失效"。
真机已验证：S6 上二维码正常显示，日志顺序是「二维码已渲染」→「开始有界轮询」。

> 注：这台设备上 B站首次申请二维码约需 60 秒（网络原因）——老版本这 60 秒里显示"已失效"，
> 新版本显示"加载中…"，拿到后立刻显示二维码。

### 4. 新增：代码体积监控

`tools/method-size/method_size.py`：直接读编译产物，列出每条方法的指令数，**超过 2000 报警**。
本版顺手报出还有 7 个方法超线（不在本版范围），后续版本会一直盯着。

### 已知问题 / 没做的事（如实）

- **闪退的复现实验这轮没成功**：正常 JIT 下 12 次尝试一次都没复现（历史约 40%），
  所以本版**不声称**"已证明原因并修好"，只声称把 9092 拆到 1972 并收紧了两处不变量。
- **B站「扫码 → 登录成功」没有真机验证**（需要真实账号扫码）；状态机与文案有 33 个 JVM 用例覆盖。
- 没有碰华为/荣耀控制中心卡片；没有做 B站 CDN 取流验证。
- `MainActivity` 里还有个 7000+ 指令的方法，本版未动。

### 测试与证据

- JVM 单测 **2126 个用例全绿**；`lint` 0 error。
- 真机 A/B：**7/7 形态逐节点完全一致**（折叠/歌词/队列/大屏/宽屏单栏/宽屏两栏/平板竖屏）。
- 全部证据：`docs/verification/v3.2.1/`（PROBE-SUMMARY / EQUIVALENCE / REAL-DEVICE /
  method-size-report / jit-experiment / CHANGELOG / REPORT）。
