# Ncrust v3.2.1-gpl 更新说明

> 版本：`3.2.1-gpl`（versionCode **56**）· 基于 v3.2.0
> 这一版没有新功能，只做**三个 P0 修复**与一套**方法体积监控**。

---

## 1. 修掉了那个「放着歌就突然闪退」的问题（P0）

**你看到的**：冷启动后点一首歌、或者在播放页停留一会儿，App **毫无征兆地整个退出**。

**真相**：播放器卡片是一个**单个方法就有 9092 条指令**的巨无霸（编译它的一个方法，
系统要分配 45MB 内存）。这是从 v2.0.0 起就一路带下来的结构性问题 —— 你过去遇到的
闪退，多半都是它。

**这一版做了什么**：把这个巨无霸按「三个布局分支 + 托盘 + 封面 + 背景 + 状态」拆成
**15 个部分**，最大的一块只剩 **1972 条指令**（不到原来的 1/4）。

> 说人话：以前是一张桌子上堆了所有东西，碰一下就可能整桌塌；现在是 15 个抽屉分开装。

## 2. 修掉了一个「宽度算出 0 就直接崩」的隐患（P0）

播放器左右两栏的宽度是按比例算的。这块代码里，**右栏**有一道「最小宽度」的保险，
**左栏没有** —— 一旦比例算出 0，不是"宽度变成 0"而是**整个 App 崩掉**。
这一版给两侧都装上保险，并且挡住了一个更隐蔽的情况（算出 `NaN` 时，原来的写法
**也挡不住**）。

## 3. 修掉「B站登录一打开就显示『二维码已失效』」（P0）

**你看到的**：B站扫码登录界面一打开，二维码位置直接写着「二维码已失效，请刷新」，
既不显示二维码，也扫不了。

**真相（两个原因叠在一起）**：
1. 界面把「申请二维码」和「等扫码结果」写成了**一步**：代码是先等完整轮询（最长 180 秒）
   才去画二维码 —— 也就是说**在那 180 秒里二维码根本还没被画出来**；
2. 二维码区域在"还没有图"的时候，一律显示「已失效」—— 所以打开的第一眼就是那句。

**这一版做了什么**：
- 顺序改成 **申请 → 先把二维码画出来 → 再开始轮询**；
- 二维码区域的文案分成**三档**：**加载中** / **已失效，请刷新** / **获取失败**（网络异常）；
  「还没画出来」再也不会被说成「已失效」；
- 生成失败时给的是**明确错误**和刷新入口，不是一句误导人的"已失效"；
- 每一步都有日志（申请 / 渲染 / 轮询 / 状态变化），以后再出问题不用靠猜。

**真机验证**：S6 上打开 B站登录，二维码正常显示，日志顺序是
`二维码已渲染` → `开始有界轮询`（老版本这两步是反的）。

> 顺带说明：这台设备上 B站首次申请二维码**要 60 秒左右**（网络原因，不是 App 的问题）——
> 老版本在这 60 秒里显示"已失效"，新版本显示"加载中…"，拿到之后立刻显示二维码。

## 4. 新增：代码体积监控（防下一个巨无霸）

仓库里多了一个脚本 `tools/method-size/method_size.py`：直接读编译产物，
把**每条方法有多少指令**列出来，**超过 2000 就报警**（退出码 = 1，可以直接当门禁）。

这一版顺手报出还有 **7 个方法超线**（设置注册表、部分界面等），它们**不在本版范围内**，
但从此每次都会被列出来 —— 下一版做的时候不需要重新发现。

## 5. 已知问题 / 没做的事（如实）

- **「放着歌闪退」的复现实验这轮没成功**：正常 JIT 下 12 次冷启动尝试**一次都没复现**
  （历史上大约 5 次里崩 2 次）。所以本版**不声称**"已证明是某个原因并修好了"，
  只声称：把那个 9092 条指令的方法拆到 1972，并把唯一能算出非法宽度的路径两侧都上了保险。
  真机 10 次冷启动验收全绿（详见 `docs/verification/v3.2.1/REAL-DEVICE.md`）。
- **B站「扫码 → 登录成功」这一段没有真机验证**（需要一个真实 B站账号去扫）。
  状态机与文案分档有 33 个 JVM 单测覆盖，但那不等于"真机扫过"。
- **没有碰华为 / 荣耀的控制中心卡片**（一直是明确不做的）。
- **没有做 B站 CDN 取流验证**（独立任务）。
- **`MainActivity` 里还有个 7000+ 条指令的方法**（首页整体），这版没动它。

## 6. 升级方式

- 覆盖安装即可（`versionCode 56` > v3.2.0 的 `55`），**不需要清除数据**，登录态与队列都保留。
- 装完可以自己试一下：用户 → 账号与登录 → 扫码登录 B站 → 二维码应当立刻出现。
