> 「逐字节等价」在本项目里的**可执行定义**（探针 §7 先写死，不是事后解释）：

### 1.1 采集口径（为什么平板形态要显式开面板）

两次采集之间**正在播的歌不同**（QQ 歌词比 ncm 慢），而窄屏/宽屏单栏下「歌词面板自动打开」
依赖 `lyricsReady` ⇒ 自动打开会发生也可能不发生。第一轮采集就踩到了这个坑：
`05b/06` 采到的是「单栏 vs 两栏」两个**不同状态**（差异全是 x 偏移，属于状态错配）。
第二轮改成**显式点「歌词」按钮**（`capture_tablet.py`），状态由脚本决定而不是由播放状态决定。
`06` 那次则刻意**不动面板**（沿用 05b 的两栏状态），与 before 的步骤逐字相同。

> 这条经验值得记下来：**A/B 快照的第一步不是写脚本，是把状态钉死**。

### 1.2 这层证据看不见什么（如实）

- 它看得见**布局与语义**，看不见**绘制**（截图未做像素级 diff：两次采集的歌不同，像素必然不同）；
- 它看不见**首帧 / 动画中间帧**（快照是稳定态）；
- 它看不见**重组次数**（拆分把一些重组范围收窄了，方向是"更小"，但这不改变任何可观测输出）。

## 3. 不能被自动化覆盖、只能靠人工/真机的一条

`MotionFrameClock` **恰好挂载一次**这条不变量（两处各挂一次会让动画相位每帧前进两次）——
它在代码结构里由「`PlayerCardBackdrop` 被 `PlayerCard` 无条件调用一次、且全仓库只有这一个调用点」
保证。真机 `04-bigscreen` / `05b` 两个形态里节拍类动效的表现一致，是它的间接证据；
但没有专门测「相位是否前进两次」（那需要逐帧采样）。
