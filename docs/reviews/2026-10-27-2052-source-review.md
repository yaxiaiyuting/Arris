### E01 / P2：缓存操作失败，仍持久化删除管理索引

- **触发**：删除单曲或清空离线缓存时，缓存目录打开、枚举或删除发生异常。
- **影响**：`removeSong` 虽返回 `false`，曲目信息和 URL 索引仍被删除；`clear` 吞掉异常后也清空两份索引。文件未能由这次调用删除，管理列表却已失去记录。界面忽略返回值，仍提示操作成功。下次是否重新收录取决于后续播放/扫描，不能当作当前失败已恢复。
- **源码**：`cache/OfflineAudioCache.kt:279–293,319–323`；`cache/OfflineLibrary.kt:294–304`；`ui/screen/OfflineCacheOverlay.kt:318–326,597–604`。

- **建议**：返回成功/部分成功/失败结果；只移除已确认删除的资源索引，保留失败项的管理与重试入口；界面根据结果反馈并重新核对实际状态。

## 继续核对的取消、图层与队列路径

### E08 / P2（纯状态机）：B 站扫码控制器的取消状态被在途响应覆盖

- **源码**：`bili/BiliQrLogin.kt:130–157,205–245,254–264,272–275,351–354`。`prepare` 等到申请响应后没有检查取消标志；`poll` 只在等待间隔两侧检查，等待 poll API 返回后直接 `apply`，成功还写入 `credential`。`pollOnce` 有同样的等待后缺口。
- **证据**：`EveningBiliCancelAuditProbe` 两项测试执行真实控制器，注入仅在进程内完成的 `CompletableDeferred` 接口。取消在途申请后释放响应，状态由 `CANCELLED` 变回 `WAITING`；取消在途轮询后释放成功响应，变为 `CONFIRMED` 并持有测试凭证。没有 HTTP、真实凭证、账号写入或 `finishLogin`。
- **实际入口及限制**：`ui/components/BiliQrLoginDialog.kt:150–194,201,320–322` 使用此控制器并在关闭时 `cancel()`。但 UI 退出还会取消 Compose 的协程 Job，可能独立阻断迟到响应。因此这里只确认控制器自身的取消契约失效，**没有证明用户关掉登录框后一定被重新登录或保存凭证**，也不把临时内存凭证等同于云端写入。
- **建议**：请求携带控制器代次；每次 await 后、更新状态或凭证前都核对取消与代次，重开会话也不能接纳前一轮响应。保留协程 Job 取消作为另一层保护。

### E10 / P2（静态）：队列拖拽提交缺少取消收尾和队列身份校验

- **源码**：`ui/player/QueueView.kt:190–202` 用 `interactive` 作 `pointerInput` key，却不在手势入口判断它；`219–247` 在独立组合协程作用域启动自动滚动；`251–272` 忽略 `drag` 的取消返回值，清理不在 finally；`313–320` 经弹簧动画及 150ms 等待后，仅传开始时的 `from/dropTo`。`MainActivity.kt:1374–1392` 只检查索引仍合法，随即移动当前位置的项。

- **触发/影响 B**：输入条件切换使 pointerInput 取消时，独立自动滚动任务与悬浮/隐藏状态没有 finally 收尾；普通手势被取消也可能继续按松手提交。展开子树彻底卸载会撤销组合作用域，因此不声称关闭后必然永久滚动或永远卡住。
- **建议**：用稳定队列项身份和队列修订号提交，队列变化时重定位或撤销；输入禁用时禁止新拖动；区分手势成功与取消，统一 finally 清理滚动任务及视觉状态。这里没有为协程框架行为编写镜像实现测试。
