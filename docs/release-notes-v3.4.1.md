## 修的是什么

你反馈「波形条会**尖端变平滑再变回去**」，并确认「就是 v3.4.0」。这一条 v3.4.0 **确实没修** ——
它修的是另一条（横向顿-冲），两者是**独立缺陷**。

### 根因：相位被用错了地方

旧写法看起来像「在相邻两格之间平滑滚动」：

```kotlin
val v = window[i] + (window[i + 1] - window[i]) * phase
```

但它在数学上是**把两个相邻时刻的信号线性混合** —— **时域模糊，不是平移**。
相位描述的是**位置**，却被拿去插**取值**。

同口径实测（一段带尖峰的幅度、扫 12 个相位，判据 = 峰尖度）：

| 相位 | 值插值（旧） | 几何平移（新） |
|---|---|---|
| 0.000 | 0.0191 | 0.0191 |
| 0.167 | **0.0068** | 0.0191 |
| 0.250 | **0.0034** | 0.0191 |
| 0.667 | **0.0337** | 0.0191 |
| 0.750 | **0.0339** | 0.0191 |
| **波动** | **90%** | **0%** |

摆动周期正好是柱间隔（约 100ms）—— 那就是你看到的「尖端变圆、再变尖」。

### 修法：取值保真，相位走几何

- 取值**直接取整格**（形状完全保真，不做任何时域混合）；
- 亚格相位交给 **x 平移** —— 复用了渲染层早就有的 `xShift` 参数（渐变色流动用的就是它）；
- x 范围多延伸一格补上左移露出的缺口 —— **不需要多采历史**。

### 为什么不是「中间写死」

你最初的提议是「只在左右两端做平滑、中间写死」。我量过那条路：它会让画面退回
**10Hz 整格跳变** —— 抖动率从 57.8% 升到 **166.9%**、单帧跳变 **100px**，比现状更抖。

本修法**同时**做到形状保真与平滑滑动（逐帧位移仍是 0.167 格 ≈ 16.7px）。
测试里有一条专门守住「不得退化成整格跳变」。

## 与 v3.4.0 那条的区别（不要混淆）

| | v3.4.0 修的 | 本条修的 |
|---|---|---|
| 现象 | 画面**顿一下再冲一下** | **尖端变圆再变尖** |
| 层次 | **位移** | **形状** |
| 根因 | 柱间隔在 UI 消费处倒推，被 vsync 量化 ⇒ 永不收敛 ⇒ 相位撞上限幅停住 | 相位拿去插**取值** ⇒ 时域模糊 |

两者都会表现为「抖」，但机制与修法完全不同。

## 验证

- 全量单测 **2556 用例 / 0 失败 / 192 个测试类**（新增 18 例）；
- 新增两条**互为对照**的判据：
  - `位置平移的峰尖度不随相位变化`（要求波动 = 0%）；
  - `值插值确实会让峰尖度随相位摆动`（要求 > 30%）—— 这是**永久守卫**：
    若有人把生产路径改回值插值，第一条会红，第二条记录「为什么不能改回去」。
- API 33 模拟器 release 包装机：**冷启 815 ms、无崩溃**，实际播放一首歌后
  波形绘制失败计数（`droppedCurveFrames`）为 **0**。

## ⚠️ 未验证

- **没有做视觉确认**。我量的是 `heights[]` 与位移序列，不是看画面 ——
  **最终仍需你肉眼 smoke test**。我在这块组件上已经错过 6 次，所以不把
  「仿真/单测绿灯」当成「你看到的抖动消失了」。
- **120Hz 未验证**：本环境没有高刷设备（模拟器 `fps=60.000004`）。
  新公式里不存在与刷新率挂钩的阈值，但这是推理，不是实测。
- 模拟器用 SwiftShader 软件渲染，其帧时间不可作为真机结论（铁律 16）。
