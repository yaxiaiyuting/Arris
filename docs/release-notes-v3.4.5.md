## 一、P0 · B 站曲目的收藏与播放上报被发给了网易云

> 这条是本次分诊上游时，在**本仓库自己的代码里**查出来的 —— 上游没有对应 commit。

### 现象

用 B 站音源播一首歌、点一下收藏（或点心形按钮），应用会往**网易云**的
`/eapi/radio/like` 发一条 `trackId=2305843009213817408` 这样的请求；
自然播完时还会把同一个 id 当 `id` 发进网易云的 webLog。

### 根因

B 站曲目的 id 是 `BILI_ID_FLAG or auid` —— **bit61 置位、bit62 清零**。
而 v2.5.5 / v2.6.0 立的两道跨源闸门判据都是**负向**的「`id > 0` 且**不是** QQ 合成 id」：

```
bili auid 123456   id=2305843009213817408  isQqId=false  ⇒ 旧判据放行 ✗
qq  合成 id         id=4611686018427511360  isQqId=true   ⇒ 旧判据拦下 ✓
ncm  id             id=1959528822           isQqId=false  ⇒ 旧判据放行 ✓（预期）
```

写闸门时只有两个音源，「不是 QQ」恰好等价于「是 ncm」。**B 站音源是两天后
（v3.1.0）才进来的**，没人知道还有第二处要同步改 —— 于是 B 站 id 一路放行。

两条可达路径都实测确认过调用链：

| 路径 | 触发方式 |
|---|---|
| 收藏 | 搜索页「加入曲库」对三源聚合结果一视同仁；全屏播放器的心形按钮存的是**正在播的那首** |
| 播放上报 | `PlayReporter` 走 `ReportGate.blockReason(NETEASE_WEBLOG, …)`，判据同样是 `!isQq` |

它与 v2.5.5（PlayReporter / QQ）、v2.6.0（like / QQ）修掉的两次**完全同源**。

### 修法

判据从「**不是 QQ**」改成「**是 ncm**」（正向白名单）：

```kotlin
fun isNeteaseId(id: Long): Boolean = id > 0L && sourceOfId(id) == MusicSource.NETEASE
```

用正向而不是「排除 QQ 再排除 B 站」，是因为**下一个音源进来时它默认被挡住**，
而不是默认放行 —— 后者正是这次漏掉 B 站的机制。两条链路（上报 + 写接口）
都改为委托这一个谓词，单测用穷举钉住它们不会分叉。

配套两处诚实性修正：

- 契约从「**恰好**被一个目标接受」改为「**至多**被一个目标接受」：B 站没有上报目标，
  所以两个方向都拒绝 —— 上报本就无处可去，丢掉才是对的；
- 拦截计数新增「B站→ncm」独立分栏（不并进 QQ 那栏），否则下一个看日志的人会把
   B 站的量当成 QQ 的存量。老快照缺这个 key 时归零，不崩。

**反证过**：把谓词临时改回旧的负向判据，其中 **5 条用例变红** —— 不是假防线。

## 二、收藏链路三处（移植上游 `de193ff` 与 `6b5b470` 读端）

前两处的代码在本仓库里与分叉点（上游 v1.3.1）**逐字节相同**，从未被本地改过。

### ① 读端取错了歌单

`getLikedPlaylistId` 取「**第一个** `specialType != 0`」当红心歌单。这个谓词**不唯一**：
账号里只要还有别的特殊歌单且排在前面，读端拿到的 `trackIds` 就与 like 的
**写入目标**（服务端固定的红心歌单）不是同一个。

本仓库的后果比上游记的「收藏后隔天消失」更脏：收藏库是**只加不减**的
（云端只负责追加），所以错歌单的 id 会被当成「云端有、本地没有」而
**追加进本地收藏** —— 把别的歌单的歌**导入**「我的收藏」，
同时 `liked_ids` 底表、收藏计数、「播放全部」全部以错歌单为准。

改为三级精确兜底（抽成纯函数，JVM 可单测）：
**名称**（含「我喜欢的音乐」或「喜欢的音乐」）→ `specialType == 5` → 任意特殊歌单。
名称最可靠，因为服务端固定的那个名字**用户改不了**。

### ② `like` 的 `time` 不是时间戳，通道也换了

`likeSong` 把 `time` 当 Unix 秒级时间戳发（`System.currentTimeMillis()/1000` ≈ 1.7e9），
而官方/参考实现固定为**试听秒数 `3`**；主通道原本也只有 eapi 客户端协议。

现在主通道走 weapi `/api/radio/like`（`time=3`），非 200（含风控 `-460`）才回退 eapi，
回退同样用 `time=3`；并补上 eapi 路径的脱敏可观测化（HTTP 状态 / 业务码 / 耗时，
**不记录** Cookie 与 CSRF）。

> **这一条不会让歌从列表里消失** —— 只加不减挡住了那个可见症状。
> 它修的是**这条 like 有没有真正落到云端**：没落地 ⇒ 换机/重装/清数据后丢失、
> 官方客户端与网页看不到、也不喂推荐。

### ③ 读失败不再清空「我喜欢的音乐」底表

`getLikedTrackIds` 把三种语义压进同一个 `emptyList()`：服务端**权威确认收藏为空** /
业务码非 200 / 结构异常。调用方无法区分，于是后两者会覆盖底表**并落盘** ——
一次抖动就让收藏页表头显示「0 首」、分页变空，且**重启后仍然是空**，
直到下一次成功刷新。（收藏单曲本体不会丢，只加不减保住了。）

改为显式 `Success / Failure` 并**显式校验业务码**（旧实现从不看 `code`，
所以 `-460` / 未登录都长成「收藏为空」）；只在 `Success` 时写底表，
`Failure` 保留旧值**且不触发落盘**。

**保留**了本仓库自有的截断补齐逻辑（`trackCount` 校验 + 分页补齐），
没有整文件套上游版本 —— 上游那个 commit 不含这段。

**没有拿**上游那套「云端权威才覆盖本地」的覆盖语义：那会把只加不减换回
「云端为真源」，复活 v2.6.0 修掉的「QQ 曲目加入库后刷新消失」。

## 三、`check.sh` 移出源码目录

它随早年多语言提交误入库，落在 `app/src/main/java` 的 Kotlin 源码树里，
且 `BASE_DIR` 硬编码了**另一台开发机**的绝对路径（`/home/rain/…`），换机即失效。
现已移到 `scripts/`，改为按脚本自身位置推导仓库根 —— 任何机器克隆后
直接 `bash scripts/check.sh` 即可（已实跑验证）。

## 未验证项（如实记录）

1. **真机未验证**：本版全部改动是纯逻辑与协议参数，未在真机上跑过。
   `like` 改 weapi 后**能否真正落到云端**只有在真机 + 有效登录态下才能确认；
   上游把「服务端先接受、例行审核再回滚」写在 commit message 里，那是**服务端侧推断**，
   本次没有做任何网络请求去验证它，也无法给出触发概率。
2. **红心歌单缺陷的触发率未测**：它取决于真实账号的 `/eapi/user/playlist` 里
   是否存在「另一个 `specialType != 0` 且排在红心歌单之前」的歌单 —— 需登录态请求才能判定。
   代码事实是确定的（旧谓词不唯一），触发概率不是。
3. **B 站闸门缺陷的实际发生次数未知**：修复前没有埋点，无法回溯有多少条 B 站 id
   曾经发出去过。修复后新计数只在本地私有目录累加，**绝不上报**。

## 未纳入本版（有意跳过）

- **上游的「分享歌曲链接 + 外部链接直达」**（`0b13228`）：功能确有价值，
  但照抄会产生**错误链接** —— 上游无条件拼 `music.163.com/song?id=<song.id>`，
  而本仓库的 QQ/B 站 id 带 `2^62`/`2^61` 标志位，拼出来的链接指向别的歌。
  要落就得先按音源分支并扩展解析器，属于新功能，不适合塞进一个纯修复的 patch 版。
- **上游的播放会话信封**（`afa5033` / `da07bb0`）：本仓库不在那个风险路径上
  （裸 `List<SongItem>` + 匿名 `TypeToken`，已用真实 release `mapping.txt` 验证
  `SongItem` 与 `TypeToken` 子类都没被改名），**无需移植**。
- 探针单测会顺带重写 `docs/verification/v3.2.2/probe/curve-smoothing-measurements.md`
  的耗时数字。那与本版改动无关（纯机器耗时漂移），已还原，不计入本版 diff。
